# 검증과 측정

## REQ-001

작업 전에 사용자 문제·목적 가설·범위·기대 결과·확인 방법을 연결한다. 정해지지 않은 기대 결과는 미결정으로 기록한다. 구현 가능한 부분은 진행하되 미정 기준에 의존한 완료 판정은 하지 않는다.

증거: 목적과 수용 사례가 연결된 작업 계약. 스킬: taeguk-work-contract.

REQ-001 1.1의 추가 의무는 시험 프로젝트(hoplites, acropolis, thesmothetai, archon)에서 새로 시작하는 작업에만 적용한다. hoplites, acropolis, thesmothetai는 2026-10-23 이후 시작한 작업, archon은 승인된 규칙 스냅샷이 archon `main`에 머지된 뒤 새로 시작하는 작업부터 적용한다(REQ-001 1.2, 2026-10-29). Taeguk 자체 작업과 기존 1.0 의무의 범위는 바뀌지 않는다. 시험 프로젝트에서는 새 사용자 흐름, 여러 변경에 걸친 작업, 요구 의미가 정해지지 않은 작업에 요구사항 이전의 의도 기록을 남긴다. 의도 기록은 BOSS의 원래 표현, 문제, 기대 결과, 영향받는 사용자·시스템, 제약, 미해결 질문, 상태(open, accepted, rejected, withdrawn)를 가진다. 에이전트는 초안을 작성할 수 있고 accepted는 BOSS 확인 이후에만 쓴다. 원래 표현의 비밀정보·개인정보는 가려서 기록한다. accepted 의도에서 REQ-007 요구사항을 만든다. 근거가 분명한 작은 변경은 작업 계약만 사용한다. 출시 후 관측이나 회고가 목적 가설 변경을 시사하면 새 의도 기록으로 연결한다.

의도 기록이 필요한 조건은 초기값이다. 시험 프로젝트에서 조건이 빠뜨리거나 과하게 요구한 사례를 기록하고, 요구사항 작업을 진행하며 조건 개정안을 만든다. 조건의 의미 변경은 GOV-002에 따라 BOSS 확인 후 반영한다.

## VER-003

PASS, FAIL, UNKNOWN, NOT_RUN, NOT_APPLICABLE을 이유와 함께 구분한다. 미실행·누락·환경 오류를 성공으로 처리하지 않는다. 어떤 미확인 항목이 완료를 막는지는 해당 작업의 승인된 필수 기준에 따른다.

증거: 검사별 실제 실행 결과와 원시 증거. CLI가 상태를 다룰 수 있어도 모든 필수 검사의 실행 여부를 자동 보장하지는 않는다.

## VER-004

변경 속성과 실제 위험에 맞춰 주 검사와 필요한 교차 관측을 선택한다. 서로 다른 관측 층·기대값 근거·데이터 출처를 활용하고 공유 가정과 미검증 범위를 밝힌다. 모든 작업에 모든 도구나 독립 에이전트를 강제하지 않는다.

증거: 선택 이유, 검사·교차 관측, 독립성 한계. 스킬: taeguk-plan-cross-verification. 같은 모델이 만든 코드와 테스트는 그 자체로 독립 증거가 아니다.

VER-004 1.1에서는 설계 단계의 검증 계획에 기존 도구의 충족 여부와 부족한 검증 도구의 제작 범위를 포함한다. 요구에서 가져온 oracle, 담당자·입출력·환경·권한·의존 관계, 정상/알려진 실패/경계 사례의 도구 자체 검증을 연결한다. 기존 도구가 충분하면 새 도구를 만들지 않는다. 도구 제작·검사 실행·증거 충분성 판단의 책임을 구분하며 자동 위임이나 새 실행 권한을 부여하지 않는다.

## MET-001

지표로 판단하기 전에 분모·대상 집합·수집 위치·시간창·누락·중복·단위·계산식·기준 출처를 정의하고 검증한다. 알려진 실패와 경계 사례, 원시 사건 또는 다른 출처와의 대조를 사용한다. 데이터 품질과 제품 판정을 구분하고 미확인 사건을 제거해 비율을 개선하지 않는다.

증거: 지표 정의, 수집·계산 버전, 대조 결과와 한계. 스킬: taeguk-verify-measurement. taeguk measure는 전달받은 건수의 범위만 계산하며 수집 완전성을 확인하지 않는다. 제품별 SLO·임계값은 별도 합의한다.

## REQ-006

검사 결과에 요구·검사 ID, 코드·산출물·환경·데이터·적용 규칙 버전을 연결한다. 관련 대상이나 기준이 바뀌면 결과를 재검증하거나 재사용 타당성과 한계를 명시한다. 이전 버전의 통과를 새 버전의 통과로 자동 승계하지 않는다.

증거: 실행 기록·artifact 식별·버전 참조. taeguk verify의 hash 일치는 파일 동일성만 보여 준다. 검사 상태의 진실성과 승인 여부는 별도 검증이다.

## REQ-007

적용 대상은 시험 프로젝트(hoplites, acropolis, thesmothetai, archon)에서 새로 시작하는 작업이다. 시작 기준은 REQ-001과 같다(REQ-007 1.1, 2026-10-29). Taeguk 자체 작업에는 기록 의무를 두지 않는다. 대상 작업에서 여러 작업이 참조하거나 BOSS 확인이 필요한 요구사항은 저장소의 요구사항 기록에 ID로 남긴다. 각 항목은 상태(draft, approved, superseded), 출처 의도, 기대 결과, 대표·실패·경계 수용 사례, 미결정 항목, 승인 참조를 가진다. approved는 BOSS 확인 근거가 있을 때만 쓴다. 승인된 의미가 바뀌면 기존 항목을 superseded로 남기고 원래 승인 참조를 보존한 채 새 항목과 연결한다. 구현 결과에서 기대값을 거꾸로 만들어 요구사항으로 등록하지 않는다.

여러 저장소에 걸친 제품은 공통 기록과 저장소별 기록을 함께 둔다. 공통 의도·요구사항은 상위 저장소에, 저장소 고유 요구사항은 해당 저장소에 두고 저장소별 항목은 공통 항목을 경로와 commit으로 참조한다. 요구사항 기록은 기대 결과를 담고 설계 결정은 기존 설계·ADR 문서를 참조한다.

증거: 요구사항 기록의 commit, 승인 참조, 작업 계약·상태 API의 `requirement_ref`. 기록 형식 검사는 승인의 진실성을 확인하지 않는다. 스킬: taeguk-work-contract. 승인 후 의미 변경과 착수 후 재작업은 MET-001 절차로 정의해 관측하며 임계값은 정하지 않는다.

## DEV-002

근거가 있는 문제를 하나의 의도로 수정한다. 영향 범위·보존할 동작·검증·복구 가능성과 묶음 처리 비용을 비교한다. 줄 수를 안전성의 대리 기준으로 삼지 않는다. 현재 범위 밖의 정리·추측성 확장은 다음 후보로 기록한다.

증거: 문제 재현, 변경 의도와 범위, 보존·문제 해소 검사. 스킬: taeguk-implement-small-change, taeguk-inspect-changeability. 공통 작업 크기·재시도 수치를 새로 강제하지 않는다.

DEV-002 1.1에서는 실제 요구나 반복 변경이 검증된 영역까지 수정하게 만드는 관계를 구조 개선 시그널로 검토한다. 변하는 책임·정의와 재사용 가능한 계약을 구분한다. 정책·흐름·실행기는 비한정적인 예시이며, 실제 변경에 적합한 다른 경계도 탐색한다. 특정 패턴·엔진 추출이나 기능의 무리한 통합을 강제하지 않는다. 현상 유지와 최소 분리를 비교하고 기존 증거의 적용 범위 및 새 조합 검증을 명시한다. 읽기 난이도만으로 개선하지 않으며 계약·구현·환경 변화에는 영향 재검증이 필요하다.

## VER-005

검증·리뷰·수정을 반복하는 단계는 다음을 모두 만족하면 끝낸다. 필수 검사가 VER-003 기준으로 PASS다. 평가 역할이 확정한 P0·P1 지적이 0건이다. P2 이하 지적은 반영했거나 반영하지 않은 이유를 기록했다. 작업 계약에 승인된 수용 기준이 이보다 엄격하면 그 기준을 따른다.

지적의 등급은 리뷰 도구가 붙인 등급이 아니라 평가 역할이 코드와 승인된 요구사항에 비춰 확정한다. 등급을 낮추거나 기각할 때는 이유를 기록하고 PR이나 작업 기록에 남긴다.

같은 지적이 두 번 되풀이되거나 수정이 다른 지적을 계속 낳으면 반복을 멈추고 BOSS에게 상황과 선택지를 보고한다. 이 보고는 작업 중단이나 실패 판정이 아니다. 기준을 낮춰 통과시키지 않는다(GOV-004).

증거: 회차별 리뷰 대상 SHA, 지적 목록, 평가 역할의 등급과 처리, 상향 보고 기록. 스킬: taeguk-work-contract, taeguk-codex-local-review. 반복 횟수 상한이 아니며 DEV-002의 재시도 수치 비강제와 GOV-005 후보의 범위·시간·비용 한도는 바뀌지 않는다.
