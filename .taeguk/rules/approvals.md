## Approval-2026-10-11

근거: 직전 응답에서 공통 원칙 8개와 보관 구성을 제시한 뒤 BOSS가 “응 그럼 일단 이렇게 룰도 추가해줘. 그리고 작업 진행하면서 필수로 필요한건... 기계적으로 체크하도록 빌드업하자”라고 지시했다.

등록 범위: REQ-001, GOV-004, VER-003, VER-004, MET-001, REQ-006, REL-005, DEV-002의 Taeguk 공통 원칙. 세부 본문은 제안의 의미와 기존 문서의 조건을 보존한다. 규칙 저장 형식과 참조에 대한 로컬 검사 기반을 포함한다. 수치 기준, 운영 권한, archive의 다른 후보, 규칙 자동 변경은 포함하지 않는다.

승인 근거는 대화 기록의 로컬 요약이다. 전자서명이나 별도 권한 시스템의 증명이 아니며 검사 도구도 그 진실성을 인증하지 않는다.

## Approval-2026-10-16

근거: BOSS가 “응 그 방향으로 태극에 반영해보자. 설계 단계에서 검증 계획이랑 필요한 도구 제작까지 잡고, structure_reviewer도 검증된 영역을 다시 안 건드리게 하는 관점으로 바꿔줘.”라고 지시했다.

범위: VER-004 1.1의 설계 중 검증 도구 계획·제작 책임과 DEV-002 1.1의 검증된 영역 재사용 관점. 이전에는 검증 방법을 정해도 도구 부족분의 제작 책임이 빠질 수 있었으나, 이제 같은 사례에서 재사용/수정/제작/불가와 제작 범위를 명시한다. 구조 검토는 읽기 난이도보다 실제 동반 수정과 계약 경계에 근거한다. 도구 제작과 조합 검증 비용이 추가될 수 있으며 엔진 도입·자동 위임·전역 설치를 승인한 것은 아니다.

새 작업부터 적용한다. 진행 중 작업은 기존 계획 버전을 보존하고 이 지침을 채택할 때 영향 범위와 새 계획 버전을 기록한다. 불필요한 도구 제작이나 근거 없는 분리가 반복되면 재검토하고 BOSS 승인 후 이전 지침으로 되돌린다. 런타임 강제 장치를 추가한 것은 아니다.

같은 작업의 후속 확인: BOSS가 “Policy·Workflow·Executor <- 이것만 한정은 아니고 이런 식으로 구조화할 수 있는 것들을 다양하게 가져가는게 좋을 거 같은데”라고 명확히 했다. DEV-002 1.1의 예시는 비한정적이며 변하는 책임과 검증 가능한 계약에서 다른 경계도 탐색한다. 특정 패턴 목록 확장 자체를 목표로 삼지 않는다.

## Approval-2026-10-23

근거: [의도·요구사항 기록 개정안](proposals/intent-requirement-records.md)을 제시한 뒤 BOSS가 다음과 같이 답했다. “1. 3개 다 괜찮은 거 같아. 2. 공통과 프로젝트 각각 다 있어야 할 거 같은데... 3. 동시 적용해서 차이점을 찾아봐야지 4. 요건 하면서 업데이트 하는 게 더 나을거 같고”

범위: REQ-001 1.1의 의도 기록 분리, REQ-007 1.0의 요구사항 기록, MET-001 절차에 따른 승인 후 의미 변경·착수 후 재작업 측정 정의. 여러 저장소 제품은 공통 기록과 저장소별 기록을 함께 둔다. 의도 기록 조건은 초기값이며 요구사항 작업 중 관측한 사례로 개정안을 만든다. 조건의 의미 변경은 다시 BOSS 확인을 거친다.

적용: 세 시험 프로젝트(hoplites, acropolis, thesmothetai)에 동시에 적용해 차이를 관측한다. 새로 시작하는 해당 작업부터 적용하고 진행 중 작업에는 소급하지 않는다. 시험 프로젝트 설치는 프로젝트별 dry-run 확인과 BOSS 승인을 거친다. 측정 임계값, 기계 검사, 자동 승인, 새 실행 권한은 포함하지 않는다.

되돌림: accepted되지 않은 의도 기록 누적, 기존 설계·ADR 문서와의 반복, 기록 비용 대비 재작업 감소 없음, 요구사항 기록과 작업 계약의 기대값 불일치가 재검토 신호다. 자동 되돌림 조건은 아니다. 되돌릴 때는 REQ-001 1.0으로 복원하고 REQ-007을 retired로 바꾸며 시험 프로젝트의 기록은 보존한다.

## Approval-2026-10-28

근거: [리뷰 반복 종료·상향 기준 개정안](proposals/review-loop-exit.md)의 확인 사항 네 가지를 제시한 뒤 BOSS가 "그대로 승인"이라고 답했다. 같은 날 BOSS는 기준의 내용을 공통 기준으로 확정했고("예시를 공통 기준으로"), 정식 규칙 등록은 별도 PR로 하도록 결정했다.

범위: VER-005 1.0. 리뷰 반복의 종료 조건(필수 검사 PASS, 평가 역할이 확정한 P0·P1 0건, P2 이하는 반영하거나 이유 기록, 작업 기준이 더 엄격하면 그 기준), 평가 역할의 등급 확정과 재분류 이유 기록, 상향 조건("같은 지적이 두 번 되풀이되거나 수정이 다른 지적을 계속 낳으면" BOSS 보고). "같은 지적"을 같은 위치로 좁히지 않는다. 적용 범위는 "Taeguk and explicitly assigned workflows"다. 반복 횟수 상한, GOV-005의 한도, 새 실행 권한, 기계 검사는 포함하지 않는다.

적용: 승인일 이후 새로 시작하는 작업부터 적용한다. 진행 중인 작업은 기존 판단을 유지하고, 채택할 때 기록한다. 시험 프로젝트에는 다음 설치 갱신 때 규칙 스냅샷으로 전달하며 프로젝트별 dry-run 확인과 BOSS 승인을 거친다.

되돌림: 이유를 기록하고 넘긴 P2가 나중에 실제 결함으로 반복 발견됨, 등급 재분류가 잦거나 근거가 약함, 상향 보고가 너무 잦거나 한 번도 쓰이지 않음이 재검토 신호다. 자동 되돌림 조건은 아니다. 되돌릴 때는 VER-005를 retired로 바꾸고 작업 단계 문서를 작업별 기준으로 복원한다.

## Approval-2026-10-29

근거: [archon 시험 프로젝트 추가 개정안](proposals/archon-pilot.md)을 제시한 뒤 BOSS가 개정안 승인 질문에 "그대로 승인"을 골랐다. 앞서 BOSS는 "일단 태극을 단단하게 만들어가면서 conductor라는 전환 프로젝트와 함께 태극 강화를 먼저 진행해두려고"라고 했고, archon 등록 안에 "등록하고 진행"이라고 답했다.

범위: REQ-001 1.2와 REQ-007 1.1에서 적용 대상에 archon(`sensibile/archon`)을 추가한다. 다른 의무의 의미는 바꾸지 않는다. 기존 세 프로젝트의 시작일 2026-10-23은 유지한다.

적용: archon은 승인된 규칙 스냅샷이 archon `main`에 머지된 뒤 새로 시작하는 작업부터 적용한다. 그 전에 시작한 작업에는 소급하지 않는다. 설치는 dry-run 확인을 거친다. 같은 자리의 별도 질문에서 BOSS가 Codex 전송에 "archon도 상시 허용"을, archon gate에 "태극처럼 로컬 리뷰로 전환"을 골랐다. 이 둘은 실행 권한 결정이며 이 규칙 개정의 범위가 아니다. 기록은 [구성과 실행 계약](../architecture.md)과 archon의 ADR에 둔다.

되돌림: 요구사항 기록이 upstream 계약 참조를 반복할 뿐 재작업 감소가 없음, 포팅 속도 대비 기록 비용 과다, ADR과의 충돌 반복이 재검토 신호다. 자동 되돌림 조건은 아니다. 되돌릴 때는 REQ-001 1.1, REQ-007 1.0의 적용 대상으로 복원하고 archon에 남은 기록은 보존한다.

## Approval-2026-10-29-worktree

근거: archon에 태극이 설치돼 있는데도 워크트리 지침이 적용되지 않는 원인을 보고하자 BOSS가 고칠 위치로 "태극 번들에 포함"을 골랐다. 이어서 [작업 전용 워크트리 개정안](proposals/worktree-first.md)의 확인 사항 세 가지를 제시하자 BOSS가 "그대로 승인"이라고 답했다.

범위: DEV-003 1.0. 저장소 파일을 바꾸는 개발 작업은 첫 편집 전에 작업 전용 워크트리와 브랜치를 만들고 그 안에서 구현·검증한다. base 선택 순서, 같은 작업의 재사용, 머지·종료된 PR 이후의 새 작업 판정, 기존 checkout·워크트리·미커밋 변경 보존을 포함한다. 적용 범위는 "Taeguk and installed projects"로, 설치된 프로젝트에서 태극 작업으로 지정되지 않은 일반 개발에도 적용한다. 프로젝트 `AGENTS.md`의 워크트리 규약이 기본값보다 우선한다. 워크트리 정리, 편집 위치의 기계적 차단, 새 실행 권한은 포함하지 않는다.

적용: 승인된 규칙 스냅샷이 각 프로젝트 `main`에 머지된 뒤 새로 시작하는 작업부터 적용한다. 진행 중인 작업에는 소급하지 않는다. 설치 갱신은 프로젝트별 dry-run 확인과 BOSS 승인을 거친다.

같은 작업의 후속 확인: 리뷰에서 `taeguk-test-gap`의 결함 주입이 브랜치 없는 detached 측정 워크트리에서 소스를 잠깐 고치므로 DEV-003과 충돌한다는 지적이 두 번 나왔다. VER-005 상향 보고에서 BOSS가 "A: 규칙에서 제외"를 골랐다. 그래서 측정 전용 워크트리에서 커밋하지 않고 되돌리는 임시 편집은 개발 편집이 아니라는 문장을 머지 전 DEV-003 1.0 본문에 넣었다. 메인 checkout과 다른 작업의 워크트리 밖에서 하고 원복을 확인하는 조건을 붙였다.

되돌림: 워크트리 준비 비용으로 작은 작업이 반복해서 늦어짐, 쌓인 워크트리로 디스크·혼동 문제가 반복됨, 프로젝트 규약과의 충돌 반복이 재검토 신호다. 자동 되돌림 조건은 아니다. 되돌릴 때는 DEV-003을 retired로 바꾸고 스킬 문장을 "repository worktree instructions"로 복원하며, 이미 만든 워크트리와 브랜치는 보존한다.
