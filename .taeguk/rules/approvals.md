[테스트 대역 선택 개정안](proposals/test-double-preference.md)의 결정 항목에 BOSS가 답했다. 적용 범위는 "태극과 시험 프로젝트 모두, 새로 시작하는 것까지", 언어는 "자바가 아녀도 같이 적용. 습관의 문제라", 기존 테스트는 "워커가 고치게"였다. 개정안 PR [sensibile/taeguk#42](https://github.com/sensibile/taeguk/pull/42) 머지 뒤 BOSS가 "승인, 반영해"라고 답했다.

범위: VER-007 1.0. fake·stub 우선, mock 라이브러리 사용 시 이유 기록, 구조 변경 신호를 mock으로 덮지 않음, 결과 확인 우선과 호출 검증의 조건. 적용 범위는 Taeguk과 시험 프로젝트 네 곳이며 언어와 관계없다. 같은 승인으로 데일리 정리의 실행 권한을 두 가지 바꾼다. 첫째, 정리 정의에 "실제 파일·객체로 같은 분기를 재현할 수 있는데 patch로 흉내 낸 테스트 대역, 결과 대신 호출만 검증한 테스트의 교체(테스트 파일만)"를 더한다. 둘째, 승인 뒤 각 프로젝트의 첫 실행에서 한 번만 변경 창 밖까지 테스트 전체의 mock 사용 지점을 전수 수집한다. 제품 코드에 주입 지점이 필요한 곳은 정리가 아니며 지금처럼 구조 개선 후보로 보고하고 BOSS 승인 뒤 시작한다. 범위 검사, 테스트 보강 워커의 권한, 데일리 정리가 도는 프로젝트(Taeguk, archon)는 바꾸지 않는다.

적용: Taeguk은 승인 시점 이후 새로 시작하는 작업부터 적용한다. 시험 프로젝트는 승인된 규칙 스냅샷이 그 프로젝트 `main`에 머지된 뒤 새로 시작하는 작업부터 적용하며, 설치 갱신은 프로젝트별 dry-run 확인과 BOSS 승인을 거친다. 진행 중인 작업은 시작 시점의 기준을 유지한다. hoplites, acropolis, thesmothetai의 기존 테스트는 그 프로젝트에 데일리 정리가 승인될 때까지 그대로 둔다.

되돌림: fake 관리 비용이 테스트 작성을 반복해서 막음, 구조 변경 신호의 오탐 누적이 재검토 신호다. 자동 되돌림 조건은 아니다. 그 사례를 들어 개정안을 다시 올린다. 되돌릴 때는 VER-007을 retired로 바꾸고 데일리 정리의 정리 정의와 수집 단계를 이전 문장으로 복원한다.

## Approval-2026-10-30-lessons

근거: BOSS가 [pstack](https://github.com/cursor/plugins/tree/main/pstack)의 강화 로직 검토를 요청하고 학습 수집과 강제 수단 사다리를 "1·2번부터" 진행하라고 했다. [학습 수집·강제 개정안](proposals/lesson-enforcement.md)의 확인 사항을 설명하자 BOSS가 "1번은 채택하면 되고, 2번은 두번 이상 일어나면 고민해야지"라고 답하고 "3번 처리해봐"라고 했다. BOSS가 답한 것은 세 항목 요약(1 채택, 2 두 번 조건, 3 원장 첫 후보 시범 처리)이며 개정안 확인 사항 1, 2, 6에 해당한다. 확인 사항 3은 채택한 본문에 들어 있어 1의 채택으로 함께 정해졌고, 4와 5는 따로 묻지 않았다. 같은 답에서 도구 간 기록 경계에 대해 "내 작업이잖아... 왜 니네 업체 싸움을 여기서 하고 있어"라고 했다.

범위: DEV-004 1.0. 작업 기록에서 교훈을 수집해 행 단위로 BOSS 확인을 받고, 증거와 함께 두 번 이상 관측된 실수를 구조·기계 검사·동작 테스트·문서 순으로 가능한 가장 높은 수준에서 막으며, 실수 유형 원장을 유지한다. 개정안에 있던 도구 간 기록 경계는 BOSS 지시로 승인 전에 뺐다. 이 저장소의 세션 기록과 메모리는 어느 도구든 읽을 수 있다. 다른 저장소의 기록을 읽지 않고 비밀·개인 정보를 보고·원장에 옮기지 않는 조건은 남긴다. 기존 테스트 경로나 gate에 새 검사를 연결하는 일(확인 사항 5), 예외, 규칙 등록, 새 실행 권한은 포함하지 않는다. 본문은 BOSS가 본 개정안 본문에서 도구 간 기록 경계 문장만 뺀 것이다. 같은 날 GitHub Codex 리뷰가 "명확한 지침이 있는데도 반복된 실수가 수집에서 기각된다"고 지적했다. 본문을 바꾸지 않고, 원장에 문서 수준으로 이미 있는 유형이 재발한 경우만 `taeguk-harvest-lessons` 필터가 원장으로 보낸다. 본문의 "문서 수준으로만 막은 유형이 다시 발생하면 다음 수정은 이전보다 높은 수준" 조항의 적용이다. 원장에 없는 유형으로 넓힐지는 BOSS가 정하지 않았다.

사례 검사(개정안 `정상·실패 사례 검사`): 두 스킬을 실제로 실행한 판정은 NOT_RUN이다. 원장 판정은 같은 날 사람이 확인했다. 언어 규약 P1(#21, #30)은 두 번 관측으로 후보다. `GIT_*` 상속(#34)은 한 번 관측으로 관찰 1회다. 실패 사례 세 가지는 판정 규칙이며 해당 실행 사례가 아직 없다(NOT_RUN). 오탐 확인은 시범 처리 PR의 검사에서 기록한다.

적용: 승인일 이후 끝나는 작업부터 적용한다. 원장의 첫 후보 두 건(언어 규약 P1, PR 본문의 Codex 멘션)은 BOSS가 시범 처리를 골랐다. 시험 프로젝트에는 다음 설치 갱신 때 dry-run 확인과 프로젝트별 BOSS 승인을 거쳐 전달한다.

되돌림: 수집 보고가 결정을 바꾸지 않는 교훈으로 채워짐, 새 검사의 오탐 반복, 원장과 실제의 어긋남, 수집 비용이 작업을 늦춤이 재검토 신호다. 자동 되돌림 조건은 아니다. 되돌릴 때는 DEV-004를 retired로 바꾸고 두 스킬을 보고 전용으로 되돌린다.

## Approval-2026-10-30-ver007-general

근거: VER-007 1.0 반영([sensibile/taeguk#43](https://github.com/sensibile/taeguk/pull/43)) 뒤, 시험 프로젝트에서 태극 작업으로 지정되지 않은 일반 개발에는 VER-007이 닿지 않는다고 보고했다. BOSS가 "넓혀줘"라고 답했다. (5) 시험 프로젝트에 설치할 때만 진입 문구에 VER-007 절을 더해 제안한다. 태극 진입 문구가 없는 곳(2026-10-30 기준 acropolis)은 전체 문구 안과 VER-007 절만 넣는 안을 나눠 묻는다. registry `scope`, 데일리 정리·테스트 보강 워커의 권한과 대상 프로젝트, 새 실행 권한은 바꾸지 않는다.

적용: Taeguk 자체 작업은 [1.0 승인 기록](approvals.md#approval-2026-10-30)과 같다. 시험 프로젝트는 위 (4)의 시작 기준을 따르며, 규칙 사본 설치와 진입 문구 반영은 다음 설치 갱신 때 프로젝트별 dry-run 확인과 BOSS 승인을 거친다. 진행 중인 작업에는 소급하지 않는다. 로컬 Codex 리뷰 프롬프트가 VER-007을 다루기 전까지 일반 개발에서의 효과는 UNKNOWN이다.

되돌림: 일반 개발에서 fake 작성 때문에 작은 작업이 반복해서 늦어짐, 구조 변경 신호 기록이 처리되지 않고 쌓임, 프로젝트 지침과 충돌 반복이 재검토 신호다. 자동 되돌림 조건은 아니다. 되돌릴 때는 VER-007 적용 대상·증거 문단을 1.0 문장으로 복원해 1.2로 올리고, index 예외 문장과 진입 문구의 VER-007 절을 뺀다. 이미 들어간 프로젝트 진입 문구는 다음 설치 갱신 때 BOSS 승인 뒤 교체한다.

## Approval-2026-11-04
