# 테스트 대역 규칙의 일반 개발 확대 개정안

상태: 2026-10-30 승인되어 [VER-007 1.1](../verification.md#ver-007)로 반영했다. 이 문서는 개정 근거로 보존한다. 승인 범위는 [승인 기록](../approvals.md#approval-2026-10-30-ver007-general)을 따른다.

작성: 2026-10-30. 근거: 같은 날 VER-007 1.0 반영([sensibile/taeguk#43](https://github.com/sensibile/taeguk/pull/43)) 뒤, 시험 프로젝트에서 태극 스킬을 쓰지 않는 일반 개발에는 VER-007이 닿지 않는다고 보고했다. BOSS는 "넓혀줘"라고 답했다. 원래 요청의 이유는 "습관의 문제라"였다. 적용 범위를 넓히는 것은 GOV-002에 따른 규칙 수정이다.

## 현행 규칙과 공백

- [적용 범위](../index.md#적용-범위와-우선순위)는 "Taeguk 개발과 이 구성을 사용하는 명시적으로 지정된 작업"이다. 예외는 DEV-003 하나다.
- VER-007 1.0 본문은 시험 프로젝트 네 곳을 적용 대상으로 적는다. 그러나 위 범위 문장 때문에 시험 프로젝트에서는 태극 작업으로 명시 지정된 흐름(예: `taeguk-implement-small-change`, `taeguk-test-gap`, archon의 `taeguk-daily-cleanup`)에만 적용된다.
- 설치 진입 문구(`installer/taeguk-init.md` 5단계)는 "apply Taeguk rules to explicitly assigned workflows; apply DEV-003 ... to all repository edits"다. 일반 개발 중인 에이전트는 VER-007을 읽을 근거가 없다.

## 문제 사례

2026-10-30 관측이다. 각 저장소 `origin/main`과 메인 checkout의 `AGENTS.md`를 읽기만 했다.

| 프로젝트 | 설치된 규칙 사본(`source_version`) | 태극 진입 문구 | 프로젝트 자체 대역 지침 |
|---|---|---|---|
| hoplites | 81817cf | "explicitly assigned workflows"만(DEV-003 없음) | 있음. "Mock 라이브러리는 기본적으로 사용하지 않는다", fake에 실제 구현과 공통 계약 테스트 |
| acropolis | f480b63 | 없음 | 있음. hoplites와 같은 취지 |
| thesmothetai | 57afff5 | "explicitly assigned workflows"만 | 없음 |
| archon | 81817cf | DEV-003 포함 문구 | 없음 |

- 네 곳 모두 VER-007이 들어간 사본(f10a2fc 이후)은 아직 설치되지 않았다.
- thesmothetai와 archon은 일반 개발에서 대역 선택을 안내하는 지침이 전혀 없다. BOSS가 말한 "쉽게 만든다고 좋지 못한 테스트"가 걸러지지 않는 곳이다.
- hoplites와 acropolis는 자체 지침이 이미 VER-007보다 엄격하거나 같은 방향이다. 확대해도 결과가 거의 바뀌지 않는다. 다만 구조 변경 신호를 어디에 남길지는 정하지 않았다.

## 개정안: VER-007 1.1

본문 변경은 적용 대상 문단과 증거 문단 두 곳이다. 대역 선택 기준(첫 세 문단)은 바꾸지 않는다.

적용 대상 문단 제안:

> 적용 대상은 Taeguk 자체 작업과 시험 프로젝트(hoplites, acropolis, thesmothetai, archon)에서 시작 기준 이후 새로 시작하는 작업이다. 시험 프로젝트에서는 태극 작업으로 지정되지 않은 일반 개발도 포함한다. 대상 편집은 테스트나 테스트 대역을 추가하거나 바꾸는 모든 저장소 편집이며, 테스트용 fake·helper와 주입 지점을 만들려고 바꾼 제품 코드를 포함한다. Taeguk의 시작 기준은 1.0 승인 시점(2026-10-30)이다. 시험 프로젝트에서 태극 작업으로 지정된 흐름의 시작 기준은 1.0과 같이 승인된 규칙 사본이 그 프로젝트 `main`에 머지된 시점이다. 일반 개발의 시작 기준은 1.1 규칙 사본과 VER-007을 가리키는 진입 문구가 모두 그 프로젝트 `main`에 머지된 시점이다. 프로젝트 `AGENTS.md`의 대역 지침과는 조항별로 비교한다. 같은 사항을 프로젝트 지침이 더 엄격하게 정하면 그 조항만 프로젝트 지침을 따르고, 프로젝트 지침이 다루지 않는 VER-007 조항(구조 변경 신호 기록 등)은 그대로 적용한다. 이 규칙은 프로젝트 지침을 완화하지 않는다. 이 기준은 언어와 관계없이 같다. 기존 테스트를 이 규칙만을 이유로 한 번에 재작성하지 않는다.

증거 문단 제안:

> 증거: 1.0의 적용 대상이던 작업(Taeguk 자체 작업과 시험 프로젝트에서 태극 작업으로 명시 지정된 흐름. 스킬 사용 여부와 관계없다)은 1.0과 같이 대역별 종류, 대체한 경계, 쓴 이유, 구조 변경 신호로 분류한 위치와 처리(구조 변경 또는 후속 기록)를 남긴다. mock 라이브러리를 썼다면 직접 만들지 않은 이유도 남긴다. 일반 개발은 예외만 PR 본문에 남긴다. 예외는 mock 라이브러리 사용과 직접 만들지 않은 이유, 그리고 구조 변경 신호로 분류한 위치와 처리(구조 변경 또는 `## 정리 후보` 기록)다. 직접 만든 fake·stub만 쓴 변경은 따로 기록하지 않는다. 스킬: taeguk-implement-small-change, taeguk-test-gap, taeguk-daily-cleanup.

함께 바꿀 것(채택 PR):

- `docs/rules/verification.md` VER-007 절을 위 두 문단으로 바꾼다.
- `docs/rules/index.md` 적용 범위 문장에 예외를 하나 더한다. "VER-007은 시험 프로젝트에서 테스트나 테스트 대역을 추가하거나 바꾸는 모든 저장소 편집(테스트용 fake·helper와 주입 지점을 만들려고 바꾼 제품 코드 포함)에 적용한다." 같은 파일의 이력 문장에 1.1 개정을 더한다.
- registry의 VER-007 `version`을 1.1로, `approval`을 새 승인 기록으로 바꾼다. `scope` 문자열은 그대로 둔다(대상 프로젝트는 같다). `approvals.md`에 새 승인 기록을 더한다.
- 이 개정안 상태 줄과 `proposals/index.md` 항목을 승인으로 바꾼다.
- `installer/taeguk-init.md` 5단계: 시험 프로젝트(VER-007에 적힌 hoplites, acropolis, thesmothetai, archon. 판단이 서지 않으면 BOSS에게 묻는다)에 설치할 때만 진입 문구 끝에 VER-007 절을 더해 제안한다. "...; apply DEV-003 (dedicated worktree, `.taeguk/rules/development.md`) to all repository edits; apply VER-007 (test doubles, `.taeguk/rules/verification.md`) to every edit that adds or changes tests or test doubles, including test fakes and helpers and production code changed to add an injection point." 시험 프로젝트가 아닌 곳에는 지금 문구를 그대로 제안한다. 마지막 문장의 "may not read DEV-003"도 시험 프로젝트에서는 "DEV-003 and VER-007"로 알린다. 옛 문구 교체 제안, CLAUDE.md가 `@AGENTS.md`를 가져오지 않을 때 양쪽 파일에 제안하는 기존 절차는 그대로 쓴다. 2026-10-30 기준 hoplites·thesmothetai·archon의 CLAUDE.md는 `@AGENTS.md`를 가져오고 acropolis에는 CLAUDE.md가 없어, 네 곳 모두 AGENTS.md 한 곳만 바꾸면 된다.

## 정상·실패 사례 검사

- 정상: 일반 개발 PR이 직접 만든 fake만 쓰고 기록이 없는 경우, mock 라이브러리를 쓰고 이유를 남긴 경우, 구조 변경 신호를 `## 정리 후보`에 남긴 경우는 충족이다.
- 실패: 주입 지점이 없는 내부 함수를 patch로 덮고 아무 기록도 없는 PR, 결과를 확인할 수 있는데 호출 횟수만 검증한 테스트를 새로 넣은 PR은 위반이다.
- 경계: 같은 사항에서 프로젝트 지침과 VER-007이 다른 기준을 주면 더 엄격한 쪽을 따른다. hoplites의 "mock 라이브러리 기본 미사용"은 VER-007의 "이유를 남기면 사용 가능"보다 엄격하므로 그 조항은 hoplites 지침을 따른다. 프로젝트 지침이 다루지 않는 조항은 VER-007을 그대로 적용한다.
- 이 규칙은 문서 지침이다. 기계 검사는 없다. 위반은 리뷰에서 관측하고, archon에서는 데일리 정리가 변경 창 안의 테스트를 볼 때도 관측한다. 일반 개발은 예외만 기록하므로, 기록 없이 patch로 덮은 PR은 리뷰가 잡지 않으면 증거가 남지 않는다.

## 비용·권한 영향

- 일반 개발 PR 작성 비용: 예외가 있을 때만 몇 줄이 늘어난다. 직접 만든 fake만 쓰면 비용이 없다.
- fake 작성 비용: mock보다 처음 작성이 느릴 수 있다. 1.0에서 이미 받아들인 비용이고, 범위만 일반 개발로 넓어진다.
- 관측 한계: 로컬 Codex 리뷰 프롬프트(`codex/skills/taeguk-codex-local-review/references/review-prompts.md`)는 VER-007을 언급하지 않는다. 그래서 일반 개발의 위반은 리뷰에서 걸린다는 보장이 없고, 아래 되돌림 신호도 관측하기 어렵다. 리뷰 프롬프트가 VER-007을 다루기 전까지 일반 개발에서의 효과는 UNKNOWN으로 본다. 리뷰 프롬프트 보강은 이 개정안 밖의 후속 후보다([sensibile/taeguk#43](https://github.com/sensibile/taeguk/pull/43) `## 정리 후보`).
- 권한: 새 실행 권한은 없다. 데일리 정리의 권한과 대상 프로젝트(Taeguk, archon), 테스트 보강 워커의 권한은 바꾸지 않는다. 진입 문구의 프로젝트 `AGENTS.md` 반영은 설치 절차대로 BOSS 승인 뒤에만 한다.

## 결정 항목

1. VER-007을 1.1로 개정해, 시험 프로젝트의 일반 개발 중 테스트나 테스트 대역을 추가하거나 바꾸는 모든 편집에 적용한다.
2. 일반 개발의 증거는 예외(mock 라이브러리 사용 이유, 구조 변경 신호)만 남긴다. 1.0의 적용 대상이던 작업(Taeguk 자체 작업, 시험 프로젝트의 태극 지정 흐름)의 전체 증거 요건은 그대로 둔다.
3. 프로젝트 `AGENTS.md`의 대역 지침과는 조항별로 비교해, 같은 사항에서 더 엄격한 프로젝트 조항만 따른다.
4. 시작 기준을 둘로 나눈다. 태극 지정 흐름은 1.0과 같이 규칙 사본 머지 시점이고, 일반 개발은 규칙 사본과 진입 문구가 모두 머지된 시점이다.
5. 시험 프로젝트에 설치할 때 진입 문구에 VER-007 절을 더해 제안한다. 각 프로젝트 반영은 다음 설치 갱신 때 dry-run 확인과 BOSS 승인을 거친다. acropolis처럼 태극 진입 문구가 아예 없는 곳에 전체 문구를 넣으면 "explicitly assigned workflows" 적용과 DEV-003도 함께 들어온다. 그래서 그때 전체 문구와 VER-007 절만 넣는 안을 나눠 BOSS에게 묻는다.

## 전환·되돌림 조건

- 적용: 태극 작업으로 지정된 흐름은 1.0과 같이 승인된 규칙 사본이 각 프로젝트 `main`에 머지된 뒤 새로 시작하는 작업부터 적용한다. 일반 개발은 1.1 규칙 사본과 새 진입 문구가 모두 머지된 뒤 새로 시작하는 작업부터 적용한다. 진행 중인 작업에는 소급하지 않는다. Taeguk 자체 작업은 1.0과 같다.
- 되돌림 신호: 일반 개발에서 fake 작성 때문에 작은 작업이 반복해서 늦어짐, 구조 변경 신호 기록이 쌓이기만 하고 처리되지 않음, 프로젝트 지침과의 충돌이 반복됨. 자동 되돌림 조건은 아니다. 그 사례를 들어 개정안을 다시 올린다.
- 되돌릴 때: VER-007을 1.0 적용 대상·증거 문단으로 복원하고(버전은 1.2로 올려 이력을 남긴다), index 예외 문장과 진입 문구의 VER-007 절을 뺀다. 이미 들어간 프로젝트 진입 문구는 다음 설치 갱신 때 BOSS 승인 뒤 교체한다.
