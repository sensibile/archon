# 커버리지 측정 도구 개정안

상태: 미승인 제안. BOSS 확인 전에는 현행 규칙이 아니며 실행 권한을 부여하지 않는다.

작성: 2026-10-29. 근거: 같은 날 BOSS가 "테스트 커버리지를 목표로 두면 이상한 짓을 할게 뻔하니... 그걸 측정도구 삼아서 테스트가 비는 부분을 찾고 채우는 방향으로 해야 할 거 같아"라고 했다. 테스트 빈 곳 점검(`taeguk-test-gap`)은 수동·보고만 모드로 시작하고, 이 원칙은 개정안으로 올리기로 했다.

## 현행 규칙과 공백

- MET-001 1.0: 지표로 판단하기 전에 분모·대상 집합·계산식을 정의하고 검증한다. 지표를 목표로 써도 되는지는 다루지 않는다. "제품별 SLO·임계값은 별도 합의한다"는 문장 때문에, 작업 계약에 커버리지 임계값을 수용 기준으로 넣는 것을 막는 규칙이 없다.
- VER-004 1.1: "같은 모델이 만든 코드와 테스트는 그 자체로 독립 증거가 아니다." 테스트가 실제 결함을 잡는지 확인하는 방법은 정하지 않았다.
- AGENTS.md: "Do not replace requirements with implementation-derived expected values." 작업 지침이지 규칙 ID가 없어 작업 계약에서 참조할 수 없다.

## 문제 사례

2026-10-29 첫 수동 점검(`.taeguk/test-gap/2026-10-29.md`, 로컬 보고)에서 관측했다.

1. 상태 API 인증에서 token 비교 절을 지워도 Elixir 21개 테스트가 모두 통과했다. 이 모듈의 커버리지는 78.57%였다. 남은 빈 곳이 하필 인증 우회 경로였다. 수치만 보면 "충분히 높음"으로 판단할 수 있다.
2. `taeguk_install.py`의 기본 모드를 dry-run에서 apply로 바꿔도 Python 110개 테스트가 모두 통과했다. 이 파일의 커버리지는 86%였다.
3. Python 측정에서 `source`를 `scripts`로만 잡자 skill 스크립트가 분모에서 빠졌다. umask 테스트의 subprocess 데이터 파일 4개가 권한 문제로 합산에서 조용히 빠졌다. 측정을 보정하지 않으면 수치가 바뀐다. 수치를 목표로 두면, 측정 범위를 좁혀 수치를 올리는 길이 열린다.

1·2는 커버리지 수치가 결함 검출력을 대신하지 못한다는 사례다. 3은 MET-001이 이미 다루는 측정 품질 문제지만, 목표로 쓰면 왜곡될 여지가 커진다는 사례다.

## 개정안: VER-006 1.0 (신규)

ID: 현행 VER-003~005, archive 후보 VER-001·002와 겹치지 않도록 VER-006을 쓴다.

제안 본문:

> 커버리지는 테스트가 실행하지 않은 위치를 찾는 측정 도구로만 쓴다. 커버리지 수치를 작업 목표, 수용 기준, 완료 판정, 개선 결과로 쓰지 않는다.
>
> 빈 곳을 채우는 테스트는 승인된 요구사항, 계약 문서, 규칙에서 기대값을 가져온다. 현재 구현이 돌려주는 값을 기대값으로 삼지 않는다. 기대값의 출처가 없으면 테스트를 쓰지 않고 BOSS에게 묻는다. 새 테스트는 그 동작을 깨뜨리는 결함 주입에서 실패해야 빈 곳을 채운 것으로 본다.
>
> 증거: 측정 명령·도구 버전·상태와 측정 위협, 빈 곳별 분류와 근거, 테스트별 기대값 출처와 결함 주입 결과. 스킬: taeguk-test-gap. 커버리지 측정의 정의와 대조는 MET-001을 따른다.

## 변경 전후 판정

| 사례 | 현행 | 개정 후 |
|---|---|---|
| 작업 계약에 "커버리지 90% 이상"을 수용 기준으로 적음 | 막는 규칙 없음 | 수용 기준으로 쓸 수 없다. 대신 빈 곳 목록과 분류를 근거로 필요한 테스트를 요구사항에 연결한다 |
| 빈 곳을 채우려고 현재 반환값을 그대로 assert하는 테스트를 추가함 | AGENTS.md 지침 위반이지만 규칙 ID가 없음 | VER-006 위반으로 리뷰에서 지적할 수 있다 |
| 새 테스트가 커버리지를 올렸지만 결함 주입에서도 통과함 | 판단 기준 없음 | 빈 곳을 채운 것으로 보지 않는다 |
| 기대 동작이 문서에 없는 함수(예: CLI 입력 1 MiB 상한) | 구현값으로 테스트를 쓸 수 있음 | 테스트를 쓰지 않고 BOSS에게 묻는다 |
| 데일리 정리나 일반 작업에서 커버리지를 참고해 테스트를 추가함 | 제약 없음 | 같은 규칙이 적용된다. 커버리지 상승은 PR 근거가 아니다 |

## 정상·실패 사례 검사

- 정상: 2026-10-29 보고의 제안 1~4는 각각 기대값 출처(`workflow-state-usage.md:69`, `installation.md:37`, VER-003, `workflow-state-usage.md:25-28`)와 결함 주입 결과(기존 테스트 통과 = 빈 곳 확인)를 갖췄다. 개정 후에도 통과한다.
- 실패: 보고의 #11(크기 상한)은 기대값 출처가 없다. 개정 후에는 테스트 제안이 아니라 질문으로 남아야 한다. 보고가 실제로 질문으로 분류했다.
- 경계: 생성 코드(`Router.Helpers` 등)의 0%는 측정 artifact다. 개정 후에도 테스트 대상이 아니다.

## 비용·권한 영향

- 결함 주입은 테스트 하나당 관련 suite 한 번을 더 돌린다. 2026-10-29 실행 기준으로 Python 약 46초, Rust·Elixir 각각 수 초다.
- 실행 권한은 바뀌지 않는다. 테스트 빈 곳 점검의 테스트 작성, PR, 자동 머지, 예약 실행은 이 개정과 별도로 BOSS 확인이 필요하다.
- 커버리지 도구(`coverage`, `cargo-llvm-cov`)는 로컬 개발 도구다. 저장소 의존성이나 CI 필수 체크에 넣지 않는다.

## 전환·되돌림 조건

- 전환: BOSS 확인 뒤 `verification.md`, `registry.toml`, `approvals.md`에 함께 반영하고, `taeguk-test-gap` 스킬의 원칙 절을 VER-006 참조로 바꾼다.
- 되돌림: 결함 주입 요구가 실제 작업에서 비용 대비 결함을 찾지 못하거나, 기대값 출처 요구 때문에 필요한 테스트가 반복해서 막히면 그 사례를 들어 개정안을 다시 올린다.
