# 의도·요구사항 기록 개정안

상태: 2026-10-23 BOSS 확인으로 승인. 현행 본문은 [검증과 측정](../verification.md#req-001)의 REQ-001 1.1과 [REQ-007](../verification.md#req-007)이며 승인 범위는 [승인 기록](../approvals.md#approval-2026-10-23)을 따른다. 이 문서는 개정 근거로 보존하며 실행 권한을 부여하지 않는다.

작성: 2026-10-23. 참고 자료: [The AI-native SDLC playbook](https://claude.com/ko/resources/articles/the-ai-native-sdlc-playbook)의 intent 캡처, spec, 추적성, 측정 예시. 자료의 6단계 승인 게이트, 외부 이슈 도구 동기화, 텔레메트리 전송은 현재 로컬 전용·단일 승인자 범위와 맞지 않아 제외한다.

## 적용 위치

규칙 본문과 템플릿은 Taeguk에 둔다. 실제 의도·요구사항 기록은 시험 프로젝트(hoplites, acropolis, thesmothetai)의 각 저장소에 둔다. Taeguk 저장소 자체의 작업에는 이번 개정으로 새 기록 의무를 만들지 않는다.

| 대상 | 위치 | 비고 |
| --- | --- | --- |
| 규칙 본문 | Taeguk `docs/rules/` | 승인 후 REQ-001 1.1, REQ-007 1.0 |
| 템플릿 | Taeguk `codex/skills/taeguk-work-contract/references/` | 프로젝트 설치로 시험 프로젝트에 전달 |
| 의도 기록 | 시험 프로젝트 `intent/` | 제품 단위. acropolis는 공통 기록을 상위 저장소에, 저장소별 기록을 atheum·akashic·axiom에 둔다(BOSS 확인 결과) |
| 요구사항 기록 | 시험 프로젝트 `requirements/` | 제품 영역별 파일 |

## 문제 사례

1. [workflow-state 사용법](../../workflow-state-usage.md)의 create 예시는 `requirement_ref`로 `docs/requirements.md#R1`을 가리킨다. 이 참조가 가리킬 요구사항 기록의 형식·상태·승인 표시는 어디에도 정의되어 있지 않다. 상태 API는 참조 문자열만 저장하므로 참조 대상이 없거나 바뀌어도 감지하지 못한다.
2. AGENTS.md는 요구사항 의미 변경에 BOSS 확인을 요구한다. 그러나 무엇이 승인된 의미인지 고정한 기록이 없다. 작업 계약은 작업별로 작게 만들도록 되어 있어, 여러 작업에 걸친 요구사항의 승인 상태를 보존하지 않는다.
3. REQ-001은 미정 기대 결과를 미결정으로 기록하게 한다. BOSS가 처음 말한 표현과 에이전트가 정리한 요구사항이 한 문서에 섞이면, 이후 해석 차이가 BOSS의 의도에서 왔는지 정리 과정에서 생겼는지 구분하기 어렵다.
4. Mission 가설은 반복 확인과 수습 부담을 줄이는 것이다. 요구사항이 승인 후 얼마나 흔들리는지, 구현 착수 뒤 재작업이 얼마나 생기는지 측정하는 정의가 없다.

1은 문서 대조로 확인한 사실이다. 2~4는 구조상 공백이며, 시험 프로젝트에서 실제 누락 사례는 아직 수집하지 않았다.

## 개정안 1: REQ-007 요구사항 기록 (신규)

현재: 해당 규칙 없음. REQ-006은 검사 결과를 요구 ID에 연결하라고 하지만 요구 ID의 기록 형식은 정하지 않는다. archive의 REQ-002~004 후보와 ID가 겹치지 않도록 REQ-007을 사용한다.

제안 본문:

> 여러 작업이 참조하거나 BOSS 확인이 필요한 요구사항은 저장소의 요구사항 기록에 ID로 남긴다. 각 항목은 상태(draft, approved, superseded), 출처 의도, 기대 결과, 대표·실패·경계 수용 사례, 미결정 항목, 승인 참조를 가진다. approved는 BOSS 확인 근거가 있을 때만 쓴다. 승인된 의미가 바뀌면 기존 항목을 superseded로 남기고 새 항목과 연결한다. 구현 결과에서 기대값을 거꾸로 만들어 요구사항으로 등록하지 않는다.
>
> 증거: 요구사항 기록의 commit, 승인 참조, 작업 계약·상태 API의 `requirement_ref`. 기록 형식 검사는 승인의 진실성을 확인하지 않는다.

기록 형식(템플릿 초안):

```markdown
## R-001

- 상태: draft | approved | superseded
- 출처: intent/2026-10-23-example.md
- 기대 결과: ...
- 수용 사례: 대표 ... / 실패 ... / 경계 ...
- 미결정: ...
- 승인: (approved일 때) 일자와 BOSS 확인 위치
- 대체: (superseded일 때) R-00N
```

`requirement_ref`는 `requirements/<area>.md#r-001`과 commit hash로 고정한다. 제목 anchor 형식은 Taeguk 규칙 검사의 anchor 규칙과 같다.

## 개정안 2: REQ-001 1.0 → 1.1 의도 기록 분리

현재 REQ-001 1.0: 작업 전에 사용자 문제·목적 가설·범위·기대 결과·확인 방법을 연결하고, 미정 기대 결과는 미결정으로 기록한다.

추가 본문:

> 새 사용자 흐름, 여러 변경에 걸친 작업, 또는 요구 의미가 정해지지 않은 작업은 요구사항 이전에 의도 기록을 남긴다. 의도 기록은 BOSS의 원래 표현, 문제, 기대 결과, 영향받는 사용자·시스템, 제약, 미해결 질문, 상태(open, accepted, rejected, withdrawn)를 가진다. 에이전트는 초안을 작성할 수 있고 accepted는 BOSS 확인 이후에만 쓴다. accepted 의도에서 요구사항을 만든다. 근거가 분명한 작은 변경은 기존 작업 계약만 사용한다. 출시 후 관측이나 회고가 목적 가설 변경을 시사하면 새 의도 기록으로 연결한다.

기존 1.0 본문은 그대로 유지한다. 미정 기준에 의존한 완료 판정 금지도 바뀌지 않는다.

## 개정안 3: 측정 정의 (규칙 추가 없음)

새 규칙 ID를 만들지 않는다. MET-001 1.0의 정의 절차에 따라 시험 프로젝트에서 아래 두 지표를 정의해 관측한다. 임계값과 목표치는 정하지 않는다.

| 지표 | 대상 집합·분모 | 분자 | 수집 위치 | 한계 |
| --- | --- | --- | --- | --- |
| 승인 후 의미 변경 | 관측 기간에 approved가 된 요구사항 | 그중 superseded가 된 항목 | `requirements/` git 이력 | 정당한 환경 변화와 처음 정리의 오류를 구분하지 않는다. 사유는 수작업 분류가 필요하다 |
| 착수 후 재작업 | 관측 기간에 구현을 시작한 work item | 구현 시작 뒤 요구사항 변경으로 새 work item이 연결된 항목 | 상태 API history, 작업 계약 | 연결 누락은 과소 집계된다. 소규모 표본에서 비율은 참고만 한다 |

이 지표가 개선되었다는 것만으로 사용자 가치의 근거가 되지 않는다. 결론은 taeguk-learn-from-outcome의 회고에서 원시 사례와 함께 판단한다.

## 변경 전후 판정

| 사례 | 현행 | 개정 후 |
| --- | --- | --- |
| 기대 결과가 분명한 작은 버그 수정 | 작업 계약 | 같음. 의도 기록은 NOT_APPLICABLE |
| BOSS 요청이 모호한 새 사용자 흐름 | 작업 계약에 미결정 기록, 작업이 끝나면 맥락 보존이 불분명 | open 의도 기록 → BOSS accepted → draft 요구사항 → 승인. 미정 부분 구현 보류는 현행과 같음 |
| 구현 중 요구 의미 변경 | 상태 API에서 새 work item 연결. 요구사항 문장 이력은 없음 | 기존 R을 superseded로, 새 R 추가. 재작업 지표에 집계 |
| 에이전트가 BOSS 확인 없이 approved 기록 (실패 사례) | 해당 기록 없음 | 규칙 위반. 승인 참조 누락은 검토로 발견한다. 형식 검사는 승인 진실성을 인증하지 않는다 |
| 구현 결과에서 역산한 기대값을 요구사항으로 등록 (실패 사례) | GOV-004로 금지 | 같음. REQ-007에 명시 |
| 기존 설계 문서가 있는 프로젝트 (hoplites `docs/design.md`, `docs/adr/`) | 프로젝트 문서 사용 | 중복 위험. 요구사항 기록은 설계 결정이 아닌 기대 결과만 담고 설계 문서를 참조한다 |

## 비용과 권한 영향

- 기록 비용: 조건에 해당하는 작업마다 의도·요구사항 파일 작성과 BOSS 확인 1회가 추가된다. 작은 변경에는 추가 비용이 없다.
- 시험 프로젝트 변경: 각 저장소에 `intent/`, `requirements/`가 생긴다. 프로젝트 설치로 스킬 참고가 갱신되므로 설치 dry-run 확인과 프로젝트별 BOSS 승인이 필요하다.
- 권한: 새 실행 권한, 외부 전송, 자동 승인을 만들지 않는다. approved·accepted 표기는 BOSS 확인을 기록할 뿐 인증하지 않는다.
- 기계 검사: 이번 개정에는 포함하지 않는다. 필요하면 요구사항 기록의 형식·참조 검사를 별도 후보로 다룬다.

## 전환과 되돌림

전환:

1. BOSS 확인 후 REQ-001 본문 1.1, REQ-007 1.0, registry, 승인 기록을 같은 변경으로 갱신한다.
2. taeguk-work-contract 참고에 의도·요구사항 템플릿을 추가하고 스킬 검증기로 검사한다.
3. 시험 프로젝트마다 설치 dry-run 확인 → BOSS 승인 → 적용 순서로 전달한다.
4. 진행 중인 작업에는 소급 적용하지 않는다. 새로 시작하는 해당 작업부터 적용한다.

되돌림 신호: accepted되지 않은 의도 기록이 쌓임, 기존 설계·ADR 문서와 내용이 반복됨, 기록 비용에 비해 재작업 사례가 줄지 않음, 요구사항 기록과 작업 계약이 서로 다른 기대값을 가짐. 신호는 자동 되돌림 조건이 아니며 GOV-002 재검토로 다룬다. 되돌릴 때는 REQ-001 1.0으로 복원하고 REQ-007을 retired로 바꾼다. 시험 프로젝트의 기존 기록은 삭제하지 않고 보존한다.

## BOSS 확인 결과

2026-10-23 확인 내용과 원래 질문은 다음과 같다.

1. 세 개정안 채택 여부: 세 안 모두 채택.
2. 여러 저장소 제품의 기록 위치: 공통 기록과 저장소별 기록을 모두 둔다. acropolis는 상위 저장소에 공통 기록, atheum·akashic·axiom 각 저장소에 저장소별 기록을 둔다.
3. 적용 순서: 세 시험 프로젝트에 동시에 적용해 차이를 관측한다.
4. 의도 기록 조건: 초기 조건으로 시작하고 요구사항 작업을 진행하며 갱신한다.
