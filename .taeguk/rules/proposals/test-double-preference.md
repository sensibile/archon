# 테스트 대역 선택 개정안

상태: 2026-10-30 승인되어 [VER-007 1.0](../verification.md#ver-007)으로 반영했다. 이 문서는 개정 근거로 보존한다. 승인 범위는 [승인 기록](../approvals.md#approval-2026-10-30)을 따른다.

작성: 2026-10-30. 근거: 같은 날 BOSS가 "특히 java 계통은 mock 라이브러리가 괴랄한 짓을 많이 하고 무겁게 만들기도 하고... 테스트 코드 작성상 쉽게 만든다고 좋지 못한 테스트를 만들더라고"라고 했다. 이어 "테스트 더블 사용이 필요할 땐 fake 객체 등을 활용하고 구조 변경이 필요한 영역을 mock으로 처리하려는 행위는 지양했으면 좋겠어"라고 했다.

## 현행 규칙과 공백

- `docs/rules/`의 현행 규칙 문서에는 테스트 대역을 다루는 조항이 없다.
- VER-004 1.1은 "같은 모델이 만든 코드와 테스트는 그 자체로 독립 증거가 아니다"라고 정한다. 대역이 실제 경계를 가려 테스트가 아무것도 검증하지 못하게 되는 경우는 다루지 않는다.
- [연구 기록](../../research/archive/전체-읽기-기록.md) 6·7장 정리(280–292행)에 비슷한 적용 후보가 있다. 대역을 쓴 이유와 생략한 실제 경계를 기록하고, 단순 값 객체까지 mock하지 않으며, 외부 라이브러리 래퍼는 실제 라이브러리와 통합 시험한다는 내용이다. archive라서 규칙 ID가 없고 작업 계약에서 참조할 수 없다.

## 문제 사례

BOSS가 관측한 일반 사례:

1. Java 계열 mock 라이브러리는 바이트코드 조작으로 final·static·생성자까지 바꿔치기한다. 테스트가 무거워지고 실패 원인을 추적하기 어려워진다.
2. 의존성을 주입받지 못하는 구조인데도 mock으로 바꿔치기하면 테스트가 쉽게 써진다. 그 결과 구조 문제는 그대로 남고, 테스트는 구현 내부 호출에 묶인다.

이 저장소의 관측(2026-10-30, `origin/main` ce79ce9). `unittest.mock`을 쓰는 파일은 `tests/test_install.py`, `tests/test_taeguk_install.py` 두 개다. `patch` 호출은 모두 28곳이다.

- `tests/test_install.py` 5곳(`:22`, `:77`, `:85`, `:121`, `:145`).
- `tests/test_taeguk_install.py` 23곳. 같은 모듈의 내부 함수 대체가 16곳(`source_version`, `roles`, `cargo_target_dir`, `published_commit`, `cli_bundle`, `skill_files`, `engine.payload`, `engine.is_link`)이다. `os` 모듈 교체 1곳(`:386`), `subprocess.run` 교체 3곳(`:195`, `:253`, `:262`), 환경 변수 `patch.dict` 3곳이 나머지다.

대표 사례:

| 위치 | 바꿔치기 대상 | 분류 |
|---|---|---|
| `tests/test_install.py:22` | 같은 모듈의 `payload` 함수 | 설치 묶음을 주입받지 못해서 내부 함수를 대체한다. 구조 변경 신호 |
| `tests/test_install.py:77` | 같은 모듈의 `atomic_write`를 실패하게 바꿈 | 쓰기 실패를 일으키기 어려워서 쓴다. 이유는 정당하다. 다만 실패 주입 지점을 모듈 함수 대체로 만든다 |
| `tests/test_install.py:121` | `os.lstat` 반환값 | Windows `FILE_ATTRIBUTE_REPARSE_POINT` 분기를 가짜 stat으로 재현한다. macOS·Linux의 임시 파일에는 이 속성이 없어 실제 파일로 대체할 수 없다. 재현하기 어려운 상태라 대역을 쓰는 이유는 정당하다. 다만 stat 조회를 주입받지 못해 `os.lstat`을 patch한다 |
| `tests/test_install.py:145`, `tests/test_taeguk_install.py:386` | `os` 모듈 전체를 `name='nt'`인 객체로 교체 | 플랫폼 판정을 주입받지 못해서 모듈을 바꿔치기한다. 구조 변경 신호 |
| `tests/test_taeguk_install.py:195`, `:262` | `subprocess.run`을 `fake_run`으로 교체 | 직접 만든 fake 함수다. 외부 프로세스 호출이 계약이므로 인수 확인은 정당하다. 다만 주입이 아니라 patch로 끼워 넣는다 |

이 표는 현재 테스트가 틀렸다는 판정이 아니다. 개정 후 같은 상황을 새로 만나면 어떻게 판단할지 보여 주는 사례다.

## 개정안: VER-007 1.0 (신규)

ID: 현행 VER-003~005, archive 후보 VER-001·002, 미승인 후보 VER-006(커버리지)과 겹치지 않도록 VER-007을 쓴다.

제안 본문:

> 테스트 대역이 필요하면 직접 만든 fake·stub 같은 단순한 대역을 먼저 쓴다. 프로젝트가 가진 구성 요소나 상태를 가진 구성 요소(예: 저장소)를 대신하는 fake는 같은 계약 검사를 실제 구현에도 돌려 둘이 어긋나지 않는지 확인한다. 외부 프로세스·서비스를 대신하는 fake는 그 fake가 따르는 인수·응답 계약을 테스트에 적고, 실제 대상과의 일치는 별도 통합 확인으로 남긴다. mock 라이브러리(동적 대역 생성, 호출 기대 검증, 모듈·전역·static·final·생성자 대체)는 대역을 직접 만들기 어렵거나 그 비용이 분명히 클 때만 쓰고 이유를 남긴다. 명시한 계약(인터페이스, behaviour) 경계에만 대역을 만드는 라이브러리는 직접 만든 fake와 같이 본다.
>
> 의존성을 주입받을 수 없어서 내부 함수·모듈·전역 상태·static 호출을 바꿔치기해야만 테스트가 된다면 구조 변경 신호로 본다. mock으로 덮지 않는다. 의존성을 경계로 드러내도록 구조를 바꾼다. 이번 범위에서 바꿀 수 없으면 그 위치와 근거를 PR 본문의 `## 정리 후보` 절에 남긴다.
>
> 결과나 상태가 목적이면 결과를 확인한다. 호출 횟수·순서·인수 검증은 외부 협력 자체가 계약일 때만 쓴다.
>
> 적용 대상은 Taeguk 자체 작업과 시험 프로젝트(hoplites, acropolis, thesmothetai, archon)에서 시작 기준 이후 새로 시작하는 작업이다. Taeguk의 시작 기준은 승인 시점이다. 시험 프로젝트의 시작 기준은 승인된 규칙 사본이 그 프로젝트 `main`에 머지된 시점이다. 이 기준은 언어와 관계없이 같다. 기존 테스트를 이 규칙만을 이유로 한 번에 재작성하지 않는다.
>
> 증거: 대역별 종류, 대체한 경계, 쓴 이유. mock 라이브러리를 썼다면 직접 만들지 않은 이유. 구조 변경 신호로 분류한 위치와 처리(구조 변경 또는 후속 기록).

## 변경 전후 판정

| 사례 | 현행 | 개정 후 |
|---|---|---|
| Java 서비스가 `new`로 만든 저장소를 Mockito 생성자 mock으로 대체해 테스트함 | 막는 규칙 없음 | 구조 변경 신호다. 저장소를 생성자 주입으로 바꾸고 메모리 fake 저장소를 쓴다 |
| 외부 결제 API 클라이언트를 인터페이스 뒤에 두고, 테스트에서 직접 만든 fake 클라이언트로 거절·시간 초과를 재현함 | 제약 없음 | 허용한다. fake가 따르는 응답 계약을 테스트에 적고, 실제 API와의 일치는 별도 통합 확인으로 남긴다 |

| 알림 발송이 계약인 기능에서 fake 발송기에 남은 메시지 수와 수신자를 검증함 | 제약 없음 | 허용한다. 외부 협력이 계약이다 |
| Python에서 같은 모듈의 내부 함수를 `patch.object`로 대체해야만 테스트가 됨 (`tests/test_install.py:22`와 같은 형태) | 제약 없음 | 새 테스트라면 구조 변경 신호다. 해당 값을 인자로 받게 바꾸거나 후속 작업으로 기록한다 |
| 디스크 가득 참처럼 실제로 일으키기 어려운 실패를 재현함 (`tests/test_install.py:77`과 같은 형태) | 제약 없음 | 허용한다. 실패 주입은 주입 가능한 쓰기 경계를 통해 하고, 그런 경계가 없으면 그 사실을 근거와 함께 남긴다 |
| 단순 값 객체·DTO를 mock으로 만듦 | 막는 규칙 없음 | 실제 객체를 쓴다 |

## 정상·실패 사례 검사

- 부분 충족: `tests/test_taeguk_install.py:188`의 `fake_run`은 직접 만든 fake 함수다. cargo 실행 인수(`cwd`, `CARGO_TARGET_DIR`)가 외부 협력 계약이라 인수 확인은 이 규칙에 맞는다. 끼워 넣는 방식이 patch라는 점은 구조 변경 신호다. 실제 cargo와의 통합 확인 기록도 없다.
- 실패: `tests/test_install.py:145`처럼 `os` 모듈 전체를 바꿔 플랫폼을 흉내 내는 테스트를 새로 쓰면 구조 변경 신호로 분류된다. 플랫폼 판정을 인자나 작은 함수 경계로 받게 고치거나 후속 작업으로 남긴다.
- 경계: Elixir Mox는 behaviour로 명시한 계약에만 대역을 만든다. 정의상 mock 라이브러리지만 계약 경계가 드러난 구조에서 쓰므로 구조 변경 신호가 아니고, 직접 만든 fake와 같이 "직접 만들지 않은 이유"는 기록하지 않아도 된다. 대역별 종류·대체한 경계·쓴 이유는 다른 대역과 같이 남긴다. 호출 기대 검증은 외부 협력이 계약인 경우에만 쓴다.

## 비용·권한 영향

- 새 테스트에서 구조 변경이 필요해지면 작업 범위가 커질 수 있다. 범위를 넘으면 후속 기록으로 미뤄서 현재 작업을 막지 않는다.
- fake를 직접 관리하는 비용이 생긴다. 프로젝트 소유·상태 있는 구성 요소의 fake는 실제 구현과 같은 계약 검사를 돌려 어긋남을 잡는다. 외부 대상 fake는 적힌 계약과 별도 통합 확인으로 잡는다.
- 데일리 정리의 자동 머지 범위가 넓어진다. 현행 정리 정의(`taeguk-daily-cleanup` 스킬의 Cleanup versus restructuring 절)는 호출자 없는 코드, 모듈 안 중복, 낡은 주석·이름·참조, 남은 디버그 코드, 깨진 링크로 닫혀 있다. 테스트 대역 교체는 여기에 없으므로, 결정 항목 3은 정리 정의에 새 항목을 더하는 실행 권한 변경이다. 승인 뒤 첫 실행에서 변경 창 밖까지 한 번 전수 수집하는 것(전환 조건 참조)도 현행 수집 규칙에서 벗어난다. 이 개정의 승인이 두 변경의 확인을 겸한다. 범위 검사(`check_worker_scope.py`)는 `tests/` 경로를 허용하므로 기계 검사는 바꾸지 않는다.
- 그 밖의 실행 권한은 바뀌지 않는다. 제품 코드에 주입 지점을 만드는 변경은 지금처럼 구조 개선 후보로 보고하고 BOSS 승인 뒤 시작한다.

## 결정 항목

1. 적용 범위 (2026-10-30 BOSS 결정): Taeguk 자체 작업과 시험 프로젝트(hoplites, acropolis, thesmothetai, archon) 모두에 적용한다. Taeguk에서는 승인 뒤 새로 시작하는 작업부터다. 시험 프로젝트에서는 승인된 규칙 사본이 설치기 dry-run 확인을 거쳐 그 프로젝트 `main`에 머지된 뒤 새로 시작하는 작업부터다. 진행 중인 작업은 시작 시점의 기준을 유지한다.
2. 언어 (2026-10-30 BOSS 결정): Java 계열에 한정하지 않고 모든 언어에 같은 기준을 쓴다. BOSS 표현으로 "습관의 문제"라서다. Python `patch`로 모듈을 바꿔치기하는 것도 Java의 static·생성자 mock과 같은 구조 변경 신호로 본다.
3. 기존 테스트 (2026-10-30 BOSS 결정): 이미 있는 mock 사용 지점은 워커가 찾아서 고친다. 맡는 워커는 데일리 정리(`taeguk-daily-cleanup`)다. 테스트 보강 워커는 빈 곳에 새 테스트를 더하는 역할이고 테스트 코드 밖을 바꿀 수 없어서 맞지 않는다. 다음처럼 나눈다.
   - 테스트 파일만 고쳐 해결되는 지점은 정리 항목으로 더한다. 예: 실제 파일·실제 객체로 같은 상태를 재현할 수 있는데 patch로 흉내 낸 곳, 결과를 확인할 수 있는데 호출 여부만 검증한 곳. 같은 분기를 실제로 재현할 수 있는지 확인한 뒤에만 고친다. Codex가 필요하다고 동의하면 자동 머지한다.
   - 제품 코드에 주입 지점을 만들어야 하는 지점은 patch를 없애려면 제품 코드를 바꿔야 한다. 예: `tests/test_install.py:22`, `:121`, `:145`, `tests/test_taeguk_install.py:195`, `:262`, `:386`. 테스트 안의 fake 함수(`fake_run`)도 제품 코드에 호출 경계가 없으면 patch로 끼워야 하므로 여기에 든다. 이런 지점은 책임 이동·인터페이스 변경이라 정리가 아니다. 데일리 정리는 이를 구조 개선 후보로 보고하고, BOSS 승인 뒤에 시작한다.
   - 데일리 정리는 BOSS가 그 프로젝트에 실행을 승인한 곳에서만 돈다. 현재 Taeguk과 archon이다. 자동 머지도 범위 검사가 있는 곳에서만 켠다. hoplites, acropolis, thesmothetai의 기존 테스트는 그 프로젝트에 데일리 정리가 승인될 때까지 그대로 둔다.

## 전환·되돌림 조건

- 전환: BOSS 확인 뒤 `verification.md`, `registry.toml`, `approvals.md`에 함께 반영한다. 테스트를 쓰는 스킬(`taeguk-test-gap` 등)의 원칙 절에 VER-007 참조를 추가한다. `taeguk-daily-cleanup` 스킬의 정리 정의와 후보 수집 단계에 "실제 파일·객체로 같은 분기를 재현할 수 있는데 patch로 흉내 낸 테스트 대역, 결과 대신 호출만 검증한 테스트의 교체(테스트 파일만)"를 더한다. VER-007 구조 변경 신호(제품 코드에 주입 지점이 필요한 곳)는 정리 항목이 아니라 구조 개선 후보로 보고한다고 함께 적는다. 데일리 정리는 변경 창(지난 체크포인트 이후)의 후보만 모으므로, 바뀌지 않은 기존 테스트는 그대로는 잡히지 않는다. 그래서 승인 뒤 각 프로젝트의 첫 실행에서 한 번만 테스트 전체의 mock 사용 지점을 전수 수집한다. Taeguk은 이 개정안의 문제 사례 목록을 출발점으로 쓴다. 그 뒤로는 변경 창의 새 지점만 모은다. 시험 프로젝트에는 결정 항목 1의 설치 절차로 전달한다.
- 되돌림: fake 관리 비용이 테스트 작성을 반복해서 막거나, 구조 변경 신호가 오탐으로 판정되는 사례가 쌓이면 그 사례를 들어 개정안을 다시 올린다.
