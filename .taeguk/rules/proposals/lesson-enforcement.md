# 학습 수집·강제 개정안

상태: 2026-10-30 BOSS 확인으로 승인. 현행 본문은 [개발 작업 공간](../development.md#dev-004)의 DEV-004 1.0이며 승인 범위는 [승인 기록](../approvals.md#approval-2026-10-30-lessons)을 따른다. 이 문서는 개정 근거로 보존하며 실행 권한을 부여하지 않는다.

작성: 2026-10-30. 근거: 같은 날 BOSS가 [pstack](https://github.com/cursor/plugins/tree/main/pstack)(MIT, Lauren Tan)의 강화 로직을 검토하라고 했다. 검토 결과 중 1번 학습 수집(`reflect`)과 2번 강제 수단 사다리(`correct`, encode-lessons-in-structure)를 "1·2번부터" 진행하라고 지시했다. 절차는 [`taeguk-harvest-lessons`](https://github.com/sensibile/taeguk/blob/7d0a7a82a0386651848f9b86411b2f48923acba8/codex/skills/taeguk-harvest-lessons/SKILL.md)와 [`taeguk-encode-mistake-class`](https://github.com/sensibile/taeguk/blob/7d0a7a82a0386651848f9b86411b2f48923acba8/codex/skills/taeguk-encode-mistake-class/SKILL.md) 스킬로 두었다. 작성 당시 두 스킬은 이 개정안의 기준을 제안 기본값으로만 썼다. 승인 뒤 현행 기준은 DEV-004 1.0이며, 미정인 것은 확인 사항 4·5뿐이다. 실수 유형과 강제 수단의 대응은 [실수 유형 원장](https://github.com/sensibile/taeguk/blob/7d0a7a82a0386651848f9b86411b2f48923acba8/docs/enforcement-ledger.md)에 둔다.

## 현행 규칙과 공백

- GOV-002 1.0: 통과 후 문제, 오탐, 중복 같은 재검토 신호를 나열한다. 그러나 이 신호를 누가 언제 모으는지는 정하지 않았다.
- `taeguk-self-improve`: 구체적인 회고 신호가 있어야 시작한다. `taeguk-learn-from-outcome`은 전달 뒤 사용자 결과와 목적 가설을 비교해 신호를 만든다. 그러나 작업 과정에서 에이전트가 저지른 실수, BOSS 정정, 리뷰 처리에서 교훈을 모으는 단계는 없다.
- [기계 검사와 확장 계획](../mechanical-checks.md): "먼저 관측된 누락을 자동화한다"고 정했다. 그러나 무엇을 관측된 누락으로 볼지, 자동화가 문서보다 먼저인지, 이미 문서로 적은 교훈이 다시 깨지면 어떻게 하는지는 정하지 않았다.
- registry: 승인된 규칙 13개와 제안 1개(GOV-005)가 모두 `enforcement = "guidance"`다. 규칙이 아닌 작업 교훈은 강제 수단을 기록할 곳 자체가 없다.
- DEV-002 1.1: "공통 작업 크기·재시도 수치를 새로 강제하지 않는다." 아래의 "두 번"은 재시도 수치가 아니라 유형으로 인정하는 조건이다.

## 문제 사례

모두 이 저장소에서 확인한 사례다.

1. **문서로만 막은 교훈이 다시 깨졌다.** GitHub Codex가 영어로 쓴 스킬에 "한국어로 작성하라"는 P1을 [sensibile/taeguk#21](https://github.com/sensibile/taeguk/pull/21)(2026-10-28)과 [sensibile/taeguk#30](https://github.com/sensibile/taeguk/pull/30)(2026-10-29)에서 냈다. 대응은 AGENTS.md 문장 수정이었다. 이후 재발했는지는 아무도 확인하지 않는다.
2. **교훈이 사람용 문서와 한 에이전트의 메모리에만 있다.** PR 본문의 `@codex` 문자열이 Codex 클라우드 작업을 부른 일이 sensibile/taeguk#13~#16(2026-10-25)에서 관측됐다. 막는 수단은 `docs/repository-operations.md`의 한 문장과 Claude 메모리뿐이다. PR 본문을 검사하는 기계 수단이 없다.
3. **구조는 있는데 쓰는지 아무도 확인하지 않는다.** pre-push hook의 `GIT_DIR`을 물려받은 테스트가 실제 저장소에 `core.bare=true`를 기록했다([sensibile/taeguk#34](https://github.com/sensibile/taeguk/pull/34), 2026-10-29). 깨끗한 git 환경을 만드는 코드가 `scripts/taeguk_install.py`와 `tests/test_check_worker_scope.py` 두 곳에 따로 있다. 새 테스트가 이것을 쓰는지는 검사하지 않는다.
4. **교훈이 세션 밖으로 나오지 않는다.** 위 사례의 원인과 대응은 모두 해당 세션의 대화와 Claude 메모리에 처음 기록됐다. Codex 역할은 Claude 메모리를 읽지 못한다. 세션의 교훈을 모아 추적되는 위치로 옮기는 절차가 없다.

## 개정안: DEV-004 1.0 (신규)

ID: archive 후보 DEV-001, 현행 DEV-002·DEV-003(작업 전용 워크트리)과 겹치지 않도록 DEV-004를 쓴다.

제안 본문(승인된 본문과 같다. BOSS 지시로 도구 간 기록 경계 문장만 승인 전에 뺐다):

> 작업이 남긴 교훈은 그 작업의 기록(이 저장소의 세션 기록, PR, 리뷰 처리, 워커 보고, BOSS 정정)에서 수집한다. PR·리뷰 기록·워커 보고는 비밀·개인 정보를 확인한 뒤 짧게 인용할 수 있다. 수집한 교훈은 오래 유효하고 미래의 결정을 바꾸며 기존 지침에 없는 것만 남긴다. 또 기록에서 두 번 이상 나왔거나 독립된 두 관점이 함께 짚은 것이어야 한다. 한 번만 나온 교훈은 이유를 적고 단일로 표시할 때만 남긴다. 그 밖의 교훈은 기각 이유와 함께 기록한다. 남은 교훈은 스킬 수정, 실수 유형 원장, 규칙 개정안, 개선 사이클 중 하나로 보낸다. 적용 전에 BOSS가 행 단위로 확인한다.
>
> 같은 실수가 증거와 함께 두 번 이상 관측되면 실수 유형으로 본다. 실수 유형은 구조, 기계 검사, 동작 테스트, 문서 순으로 가능한 가장 높은 수준에서 막는다. 더 높은 수준을 쓰지 못한 이유를 기록한다. 새 검사나 테스트는 실제로 일어난 실수에서 실패하고 현재 기준 버전에서 통과함을 실행으로 보인다.
>
> 실수 유형 원장은 유형마다 발생 근거, 수준, 강제 수단, gate 연결 여부를 기록한다. 문서 수준으로만 막은 유형이 다시 발생하면, 다음 수정은 이전보다 높은 수준이어야 한다.
>
> 증거: 수집 보고, 원장 행, 실제 실수에서의 실패 출력과 기준 버전에서의 통과 출력, PR. 스킬: taeguk-harvest-lessons, taeguk-encode-mistake-class.

## 정상·실패 사례 검사

승인 전에 아래 사례로 두 스킬의 판정을 확인한다. 결과는 승인 기록에 남긴다.

- 정상: 원장의 언어 규약 P1(#21, #30)은 두 번 관측돼 후보가 된다.
- 실패 사례: 같은 유형을 더 높은 수준을 검토한 기록 없이 문서 수준으로 끝내면 규칙 위반이다.
- 정상: `GIT_*` 상속 사고(#34)는 한 번 관측이라 관찰 1회로 남고 처리 대상이 아니다.
- 실패 사례: 새 검사를 실제 과거 실수(해당 커밋을 분리된 측정 워크트리에서 재현)에 돌리지 않고 강제됨으로 기록하면 규칙 위반이다.
- 실패 사례: 같은 세션의 한 관점에서 한 번만 나온 교훈을 이유 없이 채택 후보로 올리면 규칙 위반이다.
- 오탐 확인: 새 검사는 현재 `main`에서 통과해야 한다. 정상 변경을 막으면 되돌림 신호다.

## 다른 규칙과의 관계

- GOV-002: 재검토 신호의 수집 경로를 보탠다. 규칙 개정 절차와 BOSS 확인은 바꾸지 않는다.
- GOV-004: 실수 유형을 막는다는 이유로 기존 검사, 기대값, 임계값을 낮추지 않는다.
- DEV-003: 과거 실수의 재현은 분리된 측정 워크트리에서 하고 원복을 확인한다. 개발 편집이 아니다.
- DEV-002: "두 번"은 유형 인정 조건이며 작업 크기나 재시도 수치가 아니다. 실수 유형 하나를 PR 하나로 고치는 것은 DEV-002의 단일 의도와 같다.
- VER-004: 새 검사의 실패를 실제 과거 실수로 보이는 것은 같은 모델이 만든 검사를 독립 증거로 보지 않는 원칙의 적용이다.
- VER-006 후보(커버리지 측정 도구): 결함 주입으로 검사의 검출력을 확인한다는 방향이 같다. 서로 의존하지 않는다.

## 비용과 권한 영향

- 작업이 끝날 때 수집 보고를 쓰는 비용이 든다. 보고만 하므로 작업 완료를 막지 않는다.
- 기계 검사가 늘면 정상 변경을 막는 오탐이 생길 수 있다. 기준 버전에서의 통과 확인과 "추가분만 실패" 방식으로 줄인다.
- 이 저장소의 세션 기록과 메모리를 읽는다. 다른 저장소의 기록은 읽지 않고, 보고와 원장에 비밀이나 개인 정보를 옮기지 않는다. 어느 도구가 쓴 기록이든 이 Mac의 에이전트가 읽을 수 있다(2026-10-30 BOSS 확인, 아래 승인 결과).
- 기존 테스트 경로에 넣은 검사는 머지되는 순간 차단 검사가 된다. Python `tests/`는 pre-push와 CI에서, Rust·Elixir 테스트는 CI에서 돈다. 확인 사항 5가 승인되면 BOSS가 유형을 고르는 일이 그 연결의 승인을 겸한다. 그 전에는 연결 승인을 따로 받는다. 새 hook 단계, 새 CI job, 예외 추가, 규칙 등록은 계속 별도의 BOSS 확인 사항이다.
- 새 실행 권한과 자동 승인을 만들지 않는다.

## 전환과 되돌림

전환:

1. BOSS 확인 후 `development.md`(또는 BOSS가 정한 문서)에 DEV-004 1.0 본문, registry 항목(approved), 승인 기록을 같은 변경으로 추가한다.
2. 두 스킬의 Authority 절과 원장 머리말의 "제안 기본값" 문장을 DEV-004 참조로 바꾼다.
3. 승인일 이후 끝나는 작업부터 적용한다. 원장의 기존 행은 그대로 두고, 후보 행은 BOSS가 고른 순서로 처리한다.
4. 시험 프로젝트에는 다음 설치 갱신 때 규칙 스냅샷과 스킬로 전달한다. 설치 dry-run 확인과 프로젝트별 BOSS 승인을 거친다.

되돌림 신호: 수집 보고가 결정을 바꾸지 않는 교훈으로 채워짐, 새 검사의 오탐이 반복됨, 원장이 갱신되지 않아 실제와 어긋남, 수집 비용이 작업을 늦춤. 신호는 자동 되돌림 조건이 아니며 GOV-002 재검토로 다룬다. 되돌릴 때는 DEV-004를 retired로 바꾸고 두 스킬을 보고 전용으로 되돌린다.

## BOSS 확인 사항과 결과

2026-10-30 결과(BOSS는 세 항목 요약 1 채택·2 두 번 조건·3 시범 처리에 답했고, 이는 아래 1·2·6에 해당한다. 3~5는 따로 묻지 않았다): 1은 채택, 2는 "두번 이상 일어나면 고민해야지"로 유지, 3은 채택된 본문에 포함, 4는 답이 없어 행 단위 확인을 유지, 5는 답이 없어 미정(연결은 계속 따로 승인), 6은 "3번 처리해봐"로 시범 처리. 같은 날 BOSS가 도구 간 기록 경계(세션 기록을 쓴 도구만 읽는다)에 대해 "내 작업이잖아... 왜 니네 업체 싸움을 여기서 하고 있어"라고 해서 그 경계를 본문과 스킬에서 뺐다.


1. DEV-004 1.0 채택 여부.
2. 유형 인정 조건 "증거와 함께 두 번 이상"이 맞는지. 한 번으로 낮추면 원장이 일회성 사건으로 찬다. 세 번으로 올리면 사례 1과 같은 두 번 재발이 빠진다.
3. 수준 순서(구조 → 기계 검사 → 동작 테스트 → 문서)와 반복 시 상향 의무를 공통 기준으로 둘지.
4. 수집한 교훈을 행 단위로 BOSS가 확인하는 방식을 유지할지, 문구 수정 수준의 스킬 편집은 자율 적용으로 할지.
5. BOSS가 유형을 고르면 그 유형의 검사를 기존 테스트 경로에 넣어 pre-push와 CI에 연결하는 것까지 승인한 것으로 볼지.
6. 원장 첫 후보 두 건(언어 규약 P1, `@codex` 멘션)을 승인 전에 시범으로 처리할지.
