# 리뷰 반복 수렴 기준 개정안

상태: 2026-11-04 BOSS 확인으로 승인되어 [VER-005 1.1](../verification.md#ver-005)로 반영했다. 승인 범위는 [승인 기록](../approvals.md#approval-2026-11-04)을 따른다. 이 문서는 개정 근거로 보존하며 실행 권한을 부여하지 않는다.

작성: 2026-11-04. 근거: 같은 날 태극 도구 강화 PR 네 건을 병렬로 진행했는데, 리뷰 회차가 PR마다 크게 달랐다. 원인을 보고하자 BOSS가 개정 방향 두 가지를 골랐다. P2 이하 지적은 "목적·회귀만 수정"하고, 새 지적이 이어지면 "연속 3회차"에서 멈춘다. 종료·상향 기준을 바꾸는 일이므로 GOV-002에 따른 규칙 개정이다.

## 현행 규칙과 공백

VER-005 1.0의 종료 조건은 "P2 이하 지적은 반영했거나 반영하지 않은 이유를 기록했다"이다. 상향 조건은 "같은 지적이 두 번 되풀이되거나 수정이 다른 지적을 계속 낳으면"이다.

- P2 이하를 고칠지 기록할지 고르는 기준이 없다. 그래서 세션은 대부분 고치는 쪽을 고른다. 고치면 대상 head가 바뀌고, 저장소 PR 플로우(`docs/repository-operations.md` 2단계)에 따라 자체 리뷰와 Codex 리뷰를 다시 돈다. 다시 돌면 새 엣지 케이스가 나온다. 이렇게 반복이 스스로 이어진다.
- "계속 낳으면"을 언제 판정하는지 정해 두지 않았다. 같은 계열이 되풀이되면 알아보기 쉽지만, 매번 다른 지적이 나오면 세션이 이 조건을 적용하지 않는다.

## 개정안: VER-005 1.1

첫 문단(종료 조건)과 둘째 문단(등급 확정)은 바꾸지 않는다. P2 이하 처리 기준 문단을 새로 넣고, 상향 문단에 회차 기준을 더한다.

새 문단 제안(둘째 문단 뒤):

> 평가 역할은 P2 이하 지적을 고치기 전에 다음 셋 중 하나에 해당하는지 판정한다. 첫째, 작업 계약의 목적·승인된 요구사항·수용 기준을 어긴다. 둘째, 이 변경이 만든 회귀다(변경 전에는 없던 잘못된 동작). 셋째, 대상에서 관측됐거나, 승인된 입력 신뢰 경계 안의 도달 경로가 확인된다. 해당하면 반영한다. 해당하지 않으면 이 작업에서 고치지 않는다. 판정과 이유를 기록하고 필요하면 후속 후보로 남긴다. 해당하지 않는 지적을 고치는 것은 목적 확장이므로 BOSS에게 묻는다. 이 판정은 P0·P1에 적용하지 않는다.

상향 문단 제안(1.0 문장을 대체):

> 같은 지적이 두 번 되풀이되면 반복을 멈추고 BOSS에게 상황과 선택지를 보고한다. 같은 리뷰 역할이 같은 작업에서 연속 3회차 동안 매 회차 반영 대상 지적(위 판정을 거친 P2 이하, 또는 P0·P1)을 1건 이상 냈을 때도 같다. 지적이 서로 다르거나 이전 수정에서 생긴 것이어도 센다. 보고에는 회차별 대상 SHA, 지적과 처리, 남은 지적, 선택지(멈추고 기록, 계속, 범위 분리)를 넣는다. 이 보고는 작업 중단이나 실패 판정이 아니다. 기준을 낮춰 통과시키지 않는다(GOV-004).

증거 문단은 1.0 문장에 "P2 이하 지적별 반영 판정(세 기준 중 해당 항목 또는 비해당 이유)"을 더한다. 끝 문장은 바꾼다. 1.0의 "반복 횟수 상한이 아니며"를 "반복 횟수 상한이 아니다. 3회차는 보고 조건이며 몇 번까지 반복할 수 있는지는 정하지 않는다"로 고친다.

## 다른 규칙과의 관계

- DEV-002 "공통 작업 크기·재시도 수치를 새로 강제하지 않는다": 3회차는 반복 상한이 아니라 보고 조건이다. 1.0의 "두 번"과 같은 성격이고, 수치는 2026-11-04 BOSS가 골랐다.
- GOV-005(제안): 범위·시간·비용 한도는 계속 제안 상태로 둔다.
- VER-003, REQ-006: 바꾸지 않는다. 비해당으로 남긴 P2도 실행 증거가 없는 한 PASS로 바꾸지 않는다.
- 저장소 PR 플로우: Codex 지적으로 head가 바뀌면 자체 리뷰부터 다시 하는 순서는 바꾸지 않는다. 바뀌는 것은 head를 바꿀 지적이 줄어든다는 점이다.

## 정상·실패 사례 검사

위 판정표의 사례 10개 중 #54·#56·#57에 해당하는 행은 실제 PR 기록으로 판정했다. 나머지 네 사례(회귀, 전부 비해당, 실패 사례 둘)는 판정 규칙만 있고 실행 사례가 없다(NOT_RUN). #56의 각 지적이 세 기준 중 어디에 해당하는지는 표에 적은 대표 지적만 다시 판정했고, 전체를 다시 판정하지는 않았다(UNKNOWN).

## 비용과 권한 영향

- 관측되지 않은 엣지 케이스가 결함으로 남을 수 있다. 판정 이유와 후속 후보 기록으로 BOSS가 사후에 볼 수 있다.
- 상향 보고가 늘 수 있다. #57도 r1~r3 지적이 반영 대상으로 판정되면 r3에서 보고 대상이 된다. 보고는 작업 중단이 아니며 BOSS가 "계속"을 고를 수 있다.
- 평가 역할의 비해당 판정이 기준의 실질을 정한다. 근거 없는 판정은 PR 본문의 기록으로 드러나야 한다.
- 새 실행 권한, 외부 전송, 자동 승인, 기계 검사를 만들지 않는다.

## 전환과 되돌림

전환:

1. BOSS 확인 후 `verification.md`의 VER-005 본문을 1.1로 바꾸고, registry 버전과 승인 기록을 같은 변경으로 갱신한다.
2. `taeguk-codex-local-review` 1단계와 지적 처리 절, `taeguk-work-contract`의 작업 단계 참고 문서에 P2 판정 단계와 3회차 상향을 적는다.
3. 승인 뒤 새로 시작하는 작업부터 적용한다. 진행 중인 작업은 채택할 때 기록한다.
4. 시험 프로젝트에는 다음 설치 갱신 때 규칙 사본으로 전달하며, 프로젝트별 dry-run 확인과 BOSS 승인을 거친다. archon `AGENTS.md`의 "VER-005 종료 조건까지 반복" 문구는 사본 갱신으로 의미가 따라온다.

되돌림 신호: 비해당으로 남긴 P2가 나중에 실제 결함으로 반복 발견됨, 3회차 보고가 대부분 "계속"으로 끝남, 비해당 판정의 근거가 약함. 신호는 자동 되돌림 조건이 아니며 GOV-002 재검토로 다룬다. 되돌릴 때는 VER-005를 1.0 본문으로 복원해 1.2로 올리고, 스킬 문장도 되돌린다.

## BOSS 확인 사항

1. P2 판정의 세 기준(목적·요구사항 위반, 이 변경의 회귀, 관측 또는 도달 경로 확인)과 "비해당을 고치려면 BOSS에게 묻는다"가 맞는지.
2. 3회차 상향을 "같은 리뷰 역할, 같은 작업, 연속 회차, 반영 대상 지적 1건 이상"으로 세는 방식이 맞는지. 자체 리뷰와 Codex 리뷰를 따로 센다.
   - 승인 뒤 명시(2026-11-04): 한 head의 Codex 교차·보안 실행은 한 회차로 본다. 승인된 "따로 센다"의 해석이며, 규칙 본문과 [승인 기록](../approvals.md#approval-2026-11-04)에 적었다. 교차와 보안을 따로 세면 둘이 번갈아 지적할 때 어느 쪽도 3회차에 닿지 않는다(자체 리뷰 1회차 지적).
3. 적용 범위를 1.0과 같은 "Taeguk and explicitly assigned workflows"로 둘지.
