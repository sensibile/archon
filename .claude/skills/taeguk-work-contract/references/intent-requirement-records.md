# 의도·요구사항 기록

REQ-001 1.2와 REQ-007 1.1을 적용하는 기록 형식이다. 적용 대상은 시험 프로젝트에서 새로 시작한 작업뿐이다. hoplites, acropolis와 그 하위 저장소, thesmothetai는 2026-10-23 이후, archon은 승인된 규칙 스냅샷이 archon `main`에 머지된 뒤 시작한 작업이다. Taeguk 저장소, 다른 저장소, 그 이전부터 진행 중인 작업에는 새 의무를 만들지 않는다. 형식이 맞아도 BOSS 승인 사실이나 요구의 타당성을 증명하지 않는다.

## 언제 쓰는가

- 의도 기록: 새 사용자 흐름, 여러 변경에 걸친 작업, 요구 의미가 정해지지 않은 작업. 근거가 분명한 작은 변경은 작업 계약만 사용한다.
- 요구사항 기록: 여러 작업이 참조하거나 BOSS 확인이 필요한 기대 결과.
- 이 조건은 초기값이다. 조건이 빠뜨리거나 과하게 요구한 사례는 작업 결과에 남겨 개정안의 근거로 쓴다. 조건 변경은 BOSS 확인 후에만 반영한다.

## 위치

| 기록 | 단일 저장소 제품 | 여러 저장소 제품 |
| --- | --- | --- |
| 의도 | `intent/YYYY-MM-DD-<slug>.md` | 공통은 상위 저장소 `intent/`, 저장소 고유는 해당 저장소 `intent/` |
| 요구사항 | `requirements/<area>.md` | 공통은 상위 저장소 `requirements/`, 저장소 고유는 해당 저장소 `requirements/` |

저장소별 항목은 공통 항목을 경로와 commit으로 참조한다. 요구사항 기록은 기대 결과만 담고 설계 결정은 기존 설계·ADR 문서를 참조한다.

## 의도 기록

```markdown
# <제목>

- 상태: open | accepted | rejected | withdrawn
- 작성: YYYY-MM-DD, 초안 작성자
- 확인: (accepted·rejected일 때) 일자와 BOSS 확인 위치

## BOSS 원래 표현

정리하거나 바꾸지 않은 요청 문장. 비밀정보(키·토큰·비밀번호), 개인정보, 고객 데이터, 비공개 로그는 `[가림: 종류]`로 바꾸고 필요하면 보호된 원본 위치만 참조한다.

## 문제

## 기대 결과

## 영향받는 사용자·시스템

## 제약

## 미해결 질문

## 연결

공통 의도, 이전 회고·관측, 만들어진 요구사항 ID.
```

에이전트는 초안을 open으로 작성한다. 원래 표현의 의미와 문장은 보존하되 위의 가림 규칙을 먼저 적용한다. 가리지 않은 비밀정보가 commit되었으면 파일 삭제만으로 해결되지 않으므로 BOSS에게 알리고 해당 비밀정보의 교체를 요청한다. accepted·rejected는 BOSS 확인 후에만 쓴다. 출시 후 관측이나 회고가 목적 가설 변경을 시사하면 새 의도 기록을 만들고 이전 기록을 연결한다.

## 요구사항 기록

```markdown
# <영역> 요구사항

## R-001

- 상태: draft | approved | superseded
- 출처: intent/YYYY-MM-DD-<slug>.md
- 공통 참조: (저장소별 항목일 때) 상위 저장소 경로와 commit
- 기대 결과: ...
- 수용 사례: 대표 ... / 실패 ... / 경계 ...
- 미결정: ...
- 승인: (approved·superseded일 때) 일자와 BOSS 확인 위치. superseded로 바꿔도 원래 승인 참조를 지우지 않는다
- 대체: (superseded일 때) 새 항목 ID, 대체 일자, 대체 승인 위치
```

approved 항목의 의미를 고치지 않는다. 의미가 바뀌면 기존 항목을 superseded로 바꾸고 새 ID를 추가한다. 오타 같은 의미 없는 수정은 commit 메시지에 이유를 남긴다. 구현 결과에서 역산한 기대값을 등록하지 않는다.

작업 계약과 상태 API의 `requirement_ref`는 한 문자열로 `<repo>:<path>#<anchor>@<commit>` 형식을 쓴다. `<repo>`는 저장소 디렉터리 이름, `<commit>`은 요구사항 기록이 들어 있는 40자리 commit SHA다. 예: `hoplites:requirements/scan.md#r-001@0123456789abcdef0123456789abcdef01234567`. 공통 참조도 같은 형식을 쓴다.

## 선행 작업 연결

요구사항 변경 때문에 새 work item을 만들면 작업 계약에 다음 두 줄을 필수로 남긴다. 상태 API는 work item 사이의 관계를 저장하지 않으므로 이 계약 기록이 재작업 지표의 수집 원본이다.

```markdown
- 선행 작업: <기존 work UUID>
- 변경 사유: requirement_change <기존 R ID> -> <새 R ID>
```

요구사항 변경이 아닌 이유로 이어지는 작업은 `변경 사유`에 다른 값을 쓰고 재작업 지표에서 제외한다.

## 측정

MET-001 절차로 정의하고 임계값은 정하지 않는다. 시험 프로젝트는 같은 정의로 저장소별로 집계한다.

- 관측 기간: 반열린 구간 `[시작, 종료)`, 시간대 Asia/Seoul. 시작은 해당 저장소에 이 기록 형식이 처음 commit된 시각이다. 종료는 회고 시작 전에 정해 집계 기록에 남기며 집계 뒤에 바꾸지 않는다.
- 시각 기준: Git 사건(요구사항 상태 변경, 작업 계약 추가, 구현 commit)은 해당 commit의 committer 시각을 쓴다. 상태 API 사건은 DB에 기록된 UTC 시각을 쓴다. `start_run`은 `state_runs.started_at`, 그 밖의 명령은 history의 `created_at`이다. 비교할 때는 모두 Asia/Seoul로 바꾼다.
- 승인 후 의미 변경: 분모는 기간 안에 approved가 된 요구사항 ID 수, 분자는 그중 기간 종료 전에 superseded가 된 ID 수다. 같은 ID는 한 번만 센다. 기간 종료 뒤의 superseded는 그 기간에 넣지 않는다. 건수(분자/분모)와 비율(분자÷분모)을 함께 쓰고, 분모가 0이면 비율은 UNKNOWN이다. superseded 사유를 분류해 함께 남긴다.
- 착수 후 재작업: 분모는 착수 시각이 기간 안에 있는 work UUID 수, 분자는 그중 기간 종료 전에 `변경 사유: requirement_change`인 후속 작업 계약이 생긴 UUID 수다. 한 work UUID에 후속 작업이 여러 개여도 한 번만 센다. 건수와 비율 표기는 위와 같다. 착수 시각은 첫 구현 commit의 committer 시각과 첫 `start_run`의 `started_at` 중 이른 것이며, 하나만 있으면 그 값을 쓴다. 둘 다 없으면 착수하지 않은 것으로 보고 제외한다.
- 누락: 선행 작업 연결이 빠진 후속 작업은 분자에 들어가지 않으므로 과소 집계가 된다. 회고에서 작업 계약을 대조해 누락 건수를 따로 적는다.

지표 개선만으로 사용자 가치를 판단하지 않는다. 결론은 회고에서 원시 사례와 함께 내린다.
